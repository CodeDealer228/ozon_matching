# frida-lora-sft

LoRA SFT `ai-forever/FRIDA` (T5EncoderModel, 823M) как cross-encoder, **только
на человеческой разметке** (`matches.parquet`, 292 523 train / 73 131 val,
канонический seed-42 сплит).

- **Kaggle:** https://www.kaggle.com/code/maxamsecret/frida-lora-sft-human-only-10-epochs
- **Тип:** script · **GPU:** 1-2×T4 (код поддерживает DataParallel) · **интернет:** вкл

## История попыток: NaN loss (5 прогонов, 4 гипотезы, реальная причина — 5-я)

**№1 (fp16, LR=3e-4, 10 эпох)**: упала на первом чекпоинте (шаг 229/11430):
`ValueError: Input contains NaN` в `average_precision_score`. Симптом:
предупреждение PyTorch про `lr_scheduler.step() before optimizer.step()`
всплыло уже на 7-м шаге — `GradScaler` тихо пропускал апдейты при overflow
градиентов задолго до конца warmup, а логиты уже были NaN.
→ Гипотеза: fp16 numerical overflow. Фикс: bf16 (без `GradScaler` — не
нужен loss-scaling) + явная `torch.isfinite` проверка loss/градиента в
train loop вместо тихого `GradScaler`-скипа.

**№2 (bf16 + NaN-guard, 1 эпоха)**: `torch.OutOfMemoryError` почти сразу
после старта, хотя VRAM-probe отмерил безопасный batch=32 (11.92GB).
Причина: в ветке `if not torch.isfinite(loss)` не было `.backward()`, но и
не было `del logits, loss` — граф активаций пропущенного шага оставался в
памяти, пока следующая итерация не переприсвоит те же имена, так что на
секунду одновременно жили ДВА полных графа (~12GB каждый) на карте с 14.56GB.
Фикс: явный `del logits, loss` + `torch.cuda.empty_cache()` в этой ветке.

**№3**: пуш без `--accelerator NvidiaTeslaT4` попал на **Tesla P100**
(compute capability 6.0) — установленный PyTorch собран под `sm_70+`,
`torch.AcceleratorError: no kernel image is available`. Не баг кода, чистая
инфраструктура. Фикс: всегда явно `--accelerator NvidiaTeslaT4`.

**№4 (bf16 + утечка-фикс + T4)**: NaN на **каждом** микробатче с шага 0
(100%, не единичный сбой на старте — важное отличие от №1, где NaN начался
позже). Локальная CPU-репродукция (тот же реальный батч, та же модель,
чистый fp32 И `torch.autocast(cpu, bfloat16)`) — идеально чисто, логиты
~0.02, loss~0.86. Скан 52 224 реальных пар через collate — ни одной
вырожденной строки. → Гипотеза: fused SDPA CUDA-кернел (flash/mem-efficient)
глючит на bf16/fp16 + padding-маске на старых архитектурах вроде T4 — этот
проект уже раз наступал на SDPA-хрупкость с FRIDA (`submits/frida_probe`).
Фикс: `attn_implementation="eager"`.

**№5 (то же + eager attention)**: **тот же самый** NaN на каждом шаге с 0.
Eager не помог → гипотеза про SDPA неверна. Собран отдельный диагностический
kernel (`kaggle_kernels/frida-nan-diagnose`) — послойные хуки на все 24
блока T5, реальный батч, реальная T4, четыре варианта точности:

| вариант | результат |
|---|---|
| fp32, без autocast | чисто, loss=0.6925 |
| fp16 autocast, 1 GPU | NaN, первый плохой блок — `block.4` |
| **bf16 autocast, 1 GPU (без DataParallel)** | **чисто!** loss=0.6925 |
| bf16 autocast + `DataParallel` (2 GPU, как в реальном train) | NaN |

Ключевая улика: NaN-паттерн под `DataParallel+bf16` оказался **побитово
идентичен** результату `fp16, 1 GPU` (те же позиции NaN, те же числа в
остальных логитах) — не совпадение, а сигнатура задокументированной в самом
PyTorch ловушки: `nn.DataParallel` гонит `forward()` каждой реплики в
отдельном потоке (`parallel_apply`), и `torch.autocast`, открытый в
вызывающем потоке, **не распространяется** в эти потоки-реплики — PyTorch
сам рекомендует открывать autocast **внутри `forward()` модели**. Три места
в коде (train loop, `evaluate()`, VRAM-probe) оборачивали autocast снаружи
уже DataParallel-обёрнутого вызова — ровно неправильный паттерн.

**Настоящий фикс**: `torch.autocast(...)` перенесён внутрь
`FridaCrossEncoderClassifier.forward()` (весь код кроме этого — не менялся,
`eager`-attention и NaN-guard остаются). То же исправлено в
`frida-batch-probe` (у него тот же `DataParallel`+autocast паттерн).

Попытка №6 — **1 эпоха**, проверить реальный фикс дёшево.

## Суть

Почему не повторяем two-stage рецепт MiniLM (human + 11.19M LLM-строк из
`matches_llm.parquet`): FRIDA ~25x дороже по compute (823M против 33M) — даже
MiniLM-continue-train не влез в одну 12-часовую сессию на полном
11.48M-строчном датасете. Human-only — дешёвый, проверяемый первый шаг.

**Архитектурное решение** (весь смысл этого скрипта): токенизация **по
айтемам**, не по парам. `tokenize_to_memmap` из `lora-llm-continue-train`
перестраивает join пар против таблицы items на каждом chunk'е — это и есть
задокументированный bottleneck (~9.5ч из 12ч сессии). При ~1.007 items/pair
(почти нет реюза) выигрыша от кэширования по айтему как такового немного, но
сам join теперь дешёвый: каждый уникальный айтем токенизируется **один раз**
(`"paraphrase: " + текст`, без bos/eos) в memmap; при сборке батча
конкатенация — чистая целочисленная нарезка массивов, без единого вызова
токенайзера или join'а.

**Префикс** `"paraphrase: "` — на каждый айтем отдельно (не один инструктаж на
пару): FRIDA's own README называет этот префикс явно для
"deduplication"-задач.

**LoRA `target_modules`** проверены на реально загруженной модели (не
угаданы): `q/k/v/o` (T5Attention) + `wi_0/wi_1/wo` (gated-gelu FFN) — не
`query/key/value`, как у BERT/MiniLM. "Для всех весов" = все 7 Linear-слоёв
в каждом из 24 encoder-блоков.

**bf16, не fp16** (реверс от исходного `lora-llm-continue-train`-рецепта,
который брал fp16+GradScaler именно из-за задокументированной в CLAUDE.md/
giga3b-probe памяти: `torch.cuda.is_bf16_supported()` лжёт на T4, настоящих
bf16 tensor cores нет, эмуляция ~5x медленнее). Реверс себя оправдал —
fp16 реально NaN'ился (см. "История попыток" ниже) — но настоящей причиной
всех NaN оказался не выбор dtype, а `DataParallel`+`autocast` threading-баг,
см. там же.

## Token-budget sizing (PAIR_MAX_LENGTH) и вырезание Category

Кэш (`maxamsecret/frida-item-tokens-human`) токенизирует каждый айтем без
обрезки — 256 токенов хватает всем (711 304/711 304). Обрезка нужна только на
уровне **пары** при конкатенации, и вот что показали реальные измерения:

**`item-length-analysis`** (13.4M товаров, посимвольно, до токенизации):
`category` — лимит 64 симв., реальный максимум **23** симв., обрезка **0%** —
и при этом `category` идентична у обоих товаров пары (CLAUDE.md, проверено
100%) → нулевой различающий сигнал, чистая трата бюджета. `attributes` —
лимит 384 симв., **47% обрезается**, уже медиана режется — это где реально
живёт решающий сигнал.

**Реальная длина пары** (весь кэш + все 365 654 пар matches.parquet,
`item_lengths[row1]+item_lengths[row2]`, ДО обрезки category):

| budget | % пар обрезается | среднее потерянных токенов |
|---|---|---|
| 256 | 52.74% | 50.3 |
| 320 | 15.12% | 25.1 |
| **384** | **0.97%** | 16.7 |
| 512 (структурный потолок) | 0.00% (истинный максимум — 497) | — |

**384 — экономичный выбор с почти нулевыми потерями**: 99% пар влезают
целиком, при этом на 25% дешевле, чем всегда платить за 512.

**Вырезание `Category`** (токен-паттерн `" Category"`+`":"` = `[55917, 30]`,
`" Attributes"`+`":"` = `[91837, 30]` — стабильны независимо от контекста,
проверено векторизованным поиском на всех 711 304 айтемах, найдено 100%):
освобождает в среднем 5.6 токена/айтем, отдаёт их `Attributes`. При
PAIR_MAX_LENGTH=384 почти не заметно (и так почти ничего не режется), но при
**PAIR_MAX_LENGTH=128** — где обрезается уже **94%** пар — вырезание Category
снижает долю айтемов, вообще не долетающих до Attributes, с 0.44% до
**0.09%**. Проверено на реальном decode: `"...Name: ... Attributes: {...}"` —
без `Category:` в тексте, с реальным содержимым Attributes.

**Политика при переполнении** (`allocate_pair_budget`): честное распределение
— короткая сторона не режется сверх своей реальной длины, вся невостребованная
часть уходит другой стороне; если обе длиннее половины бюджета — делятся
поровну. Симметрично (нет причин предпочитать id1/id2), никогда не тратит
бюджет впустую.

Итог: **PAIR_MAX_LENGTH=384** — текущий выбор скрипта (почти без потерь,
экономия 25% compute). **128** — гораздо более жёсткий, но всё ещё разумный
вариант (~3x дешевле 384), если приоритет — скорость/квота, а не полнота
контента; логика вырезания Category делает его заметно менее вредным, чем
наивная обрезка "первые 128 токенов" была бы.

## Локально проверено (без GPU, до траты квоты)

- Сборка item-кэша + конкатенация в collate_fn — на реальных данных и
  реальном токенизаторе FRIDA, корректная форма батча, декодированный пример
  выглядит как ожидалось (`<s>paraphrase: Name: ... `).
- Сборка модели + один forward+backward на CPU: 11 206 656 обучаемых LoRA-
  параметров из 834 607 872 (1.34%), градиенты у LoRA-весов ненулевые
  (336 параметров с градиентом) — адаптер реально учится, не no-op.
- `allocate_pair_budget` — юнит-тесты на всех ветках (обе стороны влезают /
  одна короткая-другая длинная / обе длинные).
- Полный прогон 2000 реальных пар через loader+collate на PAIR_MAX_LENGTH=128
  И 384 — без ошибок, decode подтверждает: `Category:` отсутствует в тексте,
  `Attributes:` присутствует с реальным содержимым на обоих бюджетах.
