# qwen3-bi-encoder-lora-sft

**Не наш кернел** — работа тиммейта (Kaggle-аккаунт `grigoriyyy`, ноутбук без
осмысленного названия). Затянут в репозиторий только для документации и
чтобы код не потерялся; изменения сюда не вносим.

Первый supervised fine-tuning отдельной **bi-encoder**-ветки решения:
`Qwen/Qwen3-Embedding-0.6B` + LoRA + симметричная MLP-голова поверх пары
эмбеддингов. Архитектурно принципиально другой подход, чем наш
кросс-энкодер (MiniLM/FRIDA/BERTA) — товары кодируются независимо, пара
сравнивается post-hoc.

- **Kaggle:** https://www.kaggle.com/code/grigoriyyy/notebook8ed3b60d47
- **Тип:** notebook · **GPU:** 2×T4 (DDP, `torch.distributed.run`) · **интернет:** вкл · приватный, владелец `grigoriyyy`

## Архитектура
```
product A ─→ shared Qwen3-Embedding-0.6B ─→ eA ─┐
                                                  ├─→ |eA-eB|
product B ─→ shared Qwen3-Embedding-0.6B ─→ eB ─┤
                                                  ├─→ eA*eB
                                                  ├─→ cosine
                                                  ↓
                                           MLP 2049→512→1
                                                  ↓
                                                logit
```
- База Qwen заморожена, эмбеддинг-размерность 1024 (отсюда `2*1024+1=2049`
  на входе головы).
- LoRA `r=16, alpha=32, dropout=0.05`, `target_modules=["q_proj","k_proj","v_proj","o_proj"]`.
- LoRA и MLP-голова обучаются совместно с первого шага, без отдельной
  frozen-warmup стадии — сознательно, ради чистого первого бейзлайна.
- На валидации считаются **два** скора отдельно: `AP_mlp` (итоговый) и
  `AP_cosine` (косинус уже дообученного энкодера, без головы) — так видно,
  сколько даёт сама geometry эмбеддингов, а сколько — pair-head.
- Только 1 эпоха на первом прогоне: "сначала ровно 1 human epoch, смотрим
  clean CV, и только потом решаем, нужен ли второй".

## Чем отличается инженерно от нашего кросс-энкодерного пайплайна
- **DDP через `torch.distributed.run`, не `nn.DataParallel`** — второй
  процесс на GPU, честный NCCL-бэкенд. По конструкции не подвержен
  DataParallel+autocast NaN-ловушке, которая жрала часы GPU-квоты на
  [`../frida-nan-diagnose`](../frida-nan-diagnose).
- **Пины зависимости жёстко**: `transformers==4.57.6, sentence-transformers==5.1.2,
  peft==0.17.1, huggingface-hub==0.36.0`, `--no-deps --force-reinstall`,
  явная проверка версий новым процессом Python перед стартом — "уже ловили
  проблемы с transformers 5.x на Kaggle". Наши FRIDA/BERTA кернелы стоят на
  `transformers==5.0.0` (см. вывод `frida-nan-diagnose`) — если когда-нибудь
  берём код между ветками, версии транзитивно не совместимы бездумно.
- **FP16, не bf16** (в отличие от FRIDA/BERTA) + явный патч: обучаемые
  LoRA-параметры принудительно кастуются в fp32 поверх fp16-базы — иначе
  несовместимость с `GradScaler`.
- **Последовательная загрузка чекпоинта по rank** (rank 0, потом rank 1, с
  барьером между) — чтобы два DDP-воркера не материализовали веса
  одновременно; отдельная, независимо найденная Kaggle-специфичная
  проблема, тот же класс, что и наши OOM-находки в `lora-llm-continue-train`.
- **Ещё один, третий по счёту в проекте текстовый формат**: `Name: ...\nCategory:
  ...\nAttributes:\nkey: value\n...` — многострочный, с реальным
  `json.loads(attributes)` и сортировкой ключей. Не совпадает ни с формулой
  MiniLM из CLAUDE.md (однострочная, без парсинга JSON), ни с форматом FRIDA
  (`Name: X Category: Y Attributes: Z`, тоже без парсинга). Если этот
  bi-encoder когда-то пойдёт в сабмит — нужен свой `src/utils.py` с этой
  формулой, ни одну из двух существующих переиспользовать нельзя.
- **`MAX_LENGTH=512`** — совпадает с zero-shot бейзлайном (0.321941),
  специально чтобы не путать эффект LoRA с эффектом обрезки.

## Данные — открытый вопрос
Использует `human_pairs_5fold_item_disjoint.parquet` — **не** канонический
`data/splits/matches_split_seed42.parquet` (seed-42 80/20), а собственный
**item-disjoint 5-fold** сплит (train = folds 1-4, val = fold 0). Это более
строгая методология (ни один товар не встречается одновременно в train и
val), но источник файла не виден: `kernel-metadata.json` его не
перечисляет явно (только `maxamsecret/ozon-ecup-2026-matching` и одна
пустая строка — похоже на приватный источник, скрытый от чужих аккаунтов).
Датасетов на `grigoriyyy` через API не видно вовсе (не публикует или их
нет). **Значит: цифры этого ноутбука не на одном и том же val-сплите с
остальными результатами проекта** — сравнивать напрямую можно только
приблизительно, не как честные A/B на одном сплите (в отличие от того, как
`validate-baseline-vs-lora` намеренно сравнивает baseline/LoRA на
идентичном сплите).

## Результат
`macro_ap_mlp = 0.726`, `macro_ap_cosine` — печатается в ноутбуке, но
конкретное число не зафиксировано в коде (в файле `metrics_epoch1.json` на
Kaggle). **Лучший val-результат в проекте на сегодня** — выше BERTA (0.7111)
и намного выше обеих FRIDA (0.652 / 0.674). За 1 Kaggle-сессию, без
доупора в лимит по времени (в отличие от FRIDA/BERTA, которые упирались в
12ч).

## Планы автора (из финальной ячейки ноутбука)
1. hard-negative oversampling
2. вторая human-эпоха, если val ещё растёт
3. `r=8/16/32` LoRA-rank ablation
4. LLM-претрейн → human final fine-tune (тот же двухстадийный рецепт, что и
   у MiniLM/`lora-llm-continue-train`)
5. дистилляция с чистого кросс-энкодера
6. рантайм-оптимизация: 384/256 токенов + приоритизация SKU-critical атрибутов
