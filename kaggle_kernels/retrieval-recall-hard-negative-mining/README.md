# retrieval-recall-hard-negative-mining

Идея пользователя: не гадать, чем модель обманывается (FP-анализ), а
**воспроизвести retrieval организаторов** и напрямую проверить его через
recall@k — затем ранги 2-K, за вычетом уже размеченных, автоматически
становятся hard negatives.

- **Kaggle:** ещё не запушен
- **Тип:** script · **CPU only** · **интернет:** выкл (не нужен —
  `sklearn` уже в образе, апгрейд намеренно не делаем)

## Логика
Каждая размеченная пара `(id1, id2, target)` существует потому, что
retrieval организаторов **уже** посчитал их похожими достаточно, чтобы
показать человеку — **независимо от того, что он потом сказал** (target
0 или 1). CLAUDE.md: "Retrieval is already done by organizers". Значит все
365,654 пар — ground truth для проверки «хороший ли retrieval мы сами
построили», не только 26% позитивов.

Проверка: строим свой retrieval (TF-IDF cosine — уже показал сигнал в
[`../fasttext-category-similarity-probe`](../fasttext-category-similarity-probe)),
и для каждой размеченной пары смотрим: если запросить соседей `id1`,
на каком месте окажется `id2` (и симметрично `id2`→`id1`)? Большинство
товаров участвуют ровно в одной паре, так что recall@k здесь фактически
hit@k — либо нашли партнёра в топ-k, либо нет.

Если recall@k высокий — наш retrieval действительно воспроизводит логику
организаторов, не просто ловит попарное сходство. Тогда его **остальные**
топ-K соседи (не размеченный партнёр, и не любой другой уже размеченный
партнёр этого товара) — hard negatives по построению: настолько похожи,
что настоящий retrieval их бы тоже показал, но человеку их не показывали.
Случайная выборка из немаркированного пула такое почти никогда не найдёт.

Один проход `kneighbors()` на всю категорию против самой себя даёт сразу
и данные для recall@k, и сырьё для майнинга — не два отдельных прогона.

## Осторожность: не проверено на этом масштабе
Более ранний TF-IDF-пилот считал косинус только для 18,285 **уже
известных** пар — здесь же полный N-к-N поиск соседей внутри категории
(до ~46K товаров → потенциально ~1 млрд сравнений на категорию до
top-K extraction). sklearn считает это чанками (`pairwise_distances_chunked`
под капотом brute-force + `metric="cosine"`), не должен упасть по памяти,
но **скорость на этом масштабе не измерялась**. Поэтому категории
обрабатываются **от меньшей к большей** — если что-то пойдёт не так на
крупных категориях, результаты по меньшим всё равно останутся, и будет
видно масштабирование по факту, а не гадание заранее.

## Что на выходе
- `recall_summary.json` — recall@{1,5,10,20,50} по каждой категории,
  отдельно по направлениям (`id1→id2`, `id2→id1`, лучшее из двух).
- `mined_hard_negatives.parquet` — `(id1, id2, tfidf_cosine, category)`,
  до `K_MINE=10` новых кандидатов на товар, уже без пересечения с
  размеченными парами (ни позитивными, ни негативными). Пара может
  встретиться дважды (от `id1` и от `id2` по отдельности) при
  несимметричном соседстве — не баг, дедуп — на стороне потребителя.

## Запуск
```bash
kaggle kernels push -p kaggle_kernels/retrieval-recall-hard-negative-mining
kaggle kernels status maxamsecret/retrieval-recall-hard-negative-mining
kaggle kernels output maxamsecret/retrieval-recall-hard-negative-mining -p kaggle_kernels/retrieval-recall-hard-negative-mining/output
```
