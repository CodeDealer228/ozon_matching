# berta-lora-sft-continue-5epoch

**Подготовлено, не запущено.** Продолжение
[`../berta-lora-sft-human-only-20-epochs`](../berta-lora-sft-human-only-20-epochs)
— резюмирует `maxamsecret/berta-lora-sft-5epoch` (val macro PR-AUC
**0.7111**, `global_step=5016/22840`, ~4.4 из запланированных 20 эпох) и
проходит ещё **5 эпох**, затем останавливается.

- **Kaggle:** ещё не запушен
- **Тип:** script · **GPU:** 2×T4 (план, как у базового кернела) · **интернет:** вкл

## Найденный баг — исправлен здесь, не косметика
В `train_state.json` реального чекпоинта: `"completed_epochs": 0` при
`"global_step": 5016`. Это не опечатка, а артефакт: тот прогон писал
чекпоинты старой mid-epoch-логикой (5×/эпоху, до фикса
"только на границе эпохи"), а `completed_epochs_for_save = epoch_display
if is_epoch_end else start_epoch` — раз `is_epoch_end` ни разу не
случился до 12-часового лимита, **каждый** чекпоинт того прогона писал
`completed_epochs=0` (значение на старте прогона), независимо от того,
как далеко реально зашло обучение. `optimizer.pt`/`scheduler.pt` этим не
затронуты — там всегда настоящее состояние.

Базовый скрипт делает `start_epoch = resume_state["completed_epochs"]`,
затем `for epoch in range(start_epoch, EPOCHS)`. Довериться битому полю
как есть — значит **молча переобучить эпохи 0-3 заново** (это реальные
потраченные вычисления, не просто лишний лог), пока `global_step` идёт
дальше от честных 5016 — и расписание (cosine, `total_steps=22840`)
исчерпается где-то в середине этого незапланированного повтора: все
эпохи после этого момента будут учиться на LR≈0, без единой ошибки,
единственный видимый симптом — застывший loss. Ровно тот класс проблемы,
о котором CLAUDE.md уже предупреждает для резюма LoRA — просто другая
первопричина (протухшее поле, не смена EPOCHS).

**Фикс**: `start_epoch` теперь берётся из `global_step // steps_per_epoch`
= `5016 // 1142` = **4** — совпадает с тем, что реально показывали логи
того прогона ("epoch=5 step=5016").

## Конфиг этого прогона

| Параметр | Значение | Комментарий |
|---|---|---|
| `EPOCHS` | **20** (не менять) | Задаёт `total_steps=22840` для cosine-расписания; резюмнутое состояние optimizer/scheduler построено под это число — менять нельзя (тот же принцип, что "EPOCHS обязан остаться 1" у `frida-lora-sft-epoch3`, только тут 20). |
| `MAX_EPOCHS_THIS_RUN` | **5** (новое) | Ограничивает **цикл**, не `EPOCHS`: `for epoch in range(start_epoch, min(EPOCHS, start_epoch+5))`. Косинус-кривая на шаге N та же, что была бы у настоящего непрерывного 20-эпохного прогона — досрочная остановка её не меняет. |
| `start_epoch` (вычисляется) | **4** | `5016 // 1142`, не битое поле чекпоинта |
| `end_epoch` (вычисляется) | **9** | `min(20, 4+5)` — прогон покроет display-эпохи 5-9 из плана на 20 |
| `PAIR_MAX_LENGTH`, `LORA_*`, `LR`, `TOTAL_BATCH_SIZE` | без изменений | Байт-в-байт как у базового кернела |
| `ENABLE_DATASET_PUSH` | **False** (было `True`) | Kaggle Secrets ни разу не были настроены ни для одного реального прогона — функция ни разу не сработала, оба существующих чекпоинта опубликованы вручную. Выключено явно, а не тихо проваливается тем же образом второй раз. |
| `CHECKPOINT_DATASET_ID` | `rays0n/berta-lora-sft-checkpoint` (не используется, т.к. push выключен) | Реальный резюмируемый чекпоинт — `maxamsecret/berta-lora-sft-5epoch`, другой id. Если публикацию когда-нибудь включат обратно — поправить на аккаунт, с которого реально запущено, чтобы не расщепить историю на две линии. |

## Известное ограничение (не исправлено, осознанно)
Внешний цикл эпох не резюмится "с той же позиции внутри эпохи" — он
заново проходит **все** данные эпохи 4 (1-indexed "эпоха 5") с нуля,
просто с новым shuffle. Модель уже видела первые ~88% этой эпохи в
прошлом прогоне — небольшое повторное воздействие на данные внутри ОДНОЙ
эпохи, не 4 эпох (как было бы без фикса `start_epoch`). Батчевый резюм
потребовал бы более сложного чекпоинтинга (сохранять позицию в
DataLoader) — не запрошено, не делалось.
