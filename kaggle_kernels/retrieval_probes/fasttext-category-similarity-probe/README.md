# fasttext-category-similarity-probe

Пилот: отличает ли дешёвый CPU-only лексический сигнал известные позитивы
от известных негативов внутри **одной** категории — до того, как тратить
GPU на hard-negative mining. Категория — **Аптека**, самая сложная из 20
по доле позитивов (7.26%, минимум среди всех — посчитано напрямую по
`matches.parquet`+`items_human.parquet`, не из головы), 18,285 размеченных
пар на 35,620 уникальных товаров.

- **Kaggle:** https://www.kaggle.com/code/maxamsecret/fasttext-category-similarity-probe-pilot
- **Тип:** script · **CPU only** · **интернет:** вкл (нужен для `pip install fasttext-wheel`)

## Почему не ANCE-style
ANCE-style майнинг (гонять реальную модель по многим кандидатам, оставлять
высокоскоровые не-матчи) — стандарт для **bi-encoder'ов**: там один вектор
на товар считается один раз, дальше дешёвый nearest-neighbor поиск.
Для **cross-encoder** (BERTA у нас) это не переносится дёшево — нет
per-item вектора, каждая пара-кандидат требует отдельного полного forward.
Даже для одной категории (35,620 товаров) это ~634M пар-кандидатов —
нереально на CPU и дорого даже на GPU для пилота.

Этот кернел сначала проверяет более дешёвый вопрос: отделяет ли сигнал,
который почти ничего не стоит (TF-IDF cosine, fastText, обученный с нуля
на текстах ТОЛЬКО этой категории — CPU, без GPU, без прогона
кросс-энкодера вообще), известные позитивы от известных негативов? Если
да — сигнал сам по себе годится и как дешёвый инструмент майнинга (топ-N
соседей по cosine, всё что не в известных позитивах — негатив), и/или как
дешёвый доп.признак для головы классификатора. Если почти не разделяет —
тоже полезно знать: значит по-настоящему трудные случаи требуют более
дорогого сигнала (саму модель или attribute-level рассуждение), а дешёвый
лексический майнинг наловит в основном лёгких негативов, не трудных.

`Category` намеренно исключена из текста для fastText/TF-IDF — внутри
одной категории она константна по построению, ноль дискриминативного
сигнала (та же находка, что уже документирована в CLAUDE.md для парной
задачи в целом).

## Что считает
1. Фильтрует `matches.parquet`+`items_human.parquet` до категории Аптека.
2. Текст товара — `Name + Attributes` (обрезка как в CLAUDE.md, без Category).
3. Обучает fastText (skipgram, dim=100, epoch=5) **с нуля** только на этих
   35,620 текстах.
4. TF-IDF (1-2 grams, sklearn) — почти бесплатный бейзлайн для сравнения.
5. Косинус для всех 18,285 размеченных пар, оба сигнала, полностью
   векторизовано (без Python-цикла по парам).
6. `average_precision_score`/`roc_auc_score`: насколько один голый косинус
   (без всякой модели) отделяет позитив от негатива.

## Не запускает BERTA
Специально — чистый лексический/subword сигнал, чтобы изолированно
понять, что даёт почти бесплатный метод, прежде чем тянуться к GPU. Как
только кэш эмбеддингов BERTA (`../berta-lora-pair-cache`) будет готов —
дешёвый follow-up: посчитать те же ft_cosine/tfidf_cosine именно для
**false positives** BERTA (не только позитив/негатив вообще) — это уже
чистая CPU-математика поверх готового кэша, без нового Kaggle-прогона.

## Запуск
```bash
kaggle kernels push -p kaggle_kernels/retrieval_probes/fasttext-category-similarity-probe
kaggle kernels status maxamsecret/fasttext-category-similarity-probe-pilot
kaggle kernels output maxamsecret/fasttext-category-similarity-probe-pilot -p kaggle_kernels/retrieval_probes/fasttext-category-similarity-probe/output
```

## Результат (v1, реальный прогон)
**76.8с всего** — из них 46.2с на само обучение fastText (5 эпох,
skipgram, vocab 54,372), 7.3с на векторы товаров, 4.0с на TF-IDF, 8.4с на
`pip install`, остальное — данные/подготовка. Быстро, легко гонять на
других категориях не задумываясь о времени.

Данные подтвердили локальный расчёт один в один: Аптека — 18,285 пар,
`pos_rate=0.0726`.

| Сигнал | AP | ROC-AUC | pos_mean | neg_mean |
|---|---|---|---|---|
| fastText cosine | 0.1499 | 0.5454 | 0.8774 | 0.8705 |
| **TF-IDF cosine** | **0.1660** | **0.6253** | 0.3019 | 0.2399 |
| (baseline: случайный скор) | 0.0726 | 0.5 | — | — |

**Неожиданно: TF-IDF обыграл fastText** — и по качеству (AP 0.166 vs
0.150, ROC-AUC 0.625 vs 0.545), и по цене (4с vs 53.5с). Вероятная причина
видна в самих числах: у fastText `pos_mean=0.877` и `neg_mean=0.871` —
почти совпадают и оба близки к 1.0, то есть векторы почти всех товаров
свалились в одну кучу (мало данных на категорию — 35,620 коротких
текстов, 5 эпох — не хватает, чтобы выучить осмысленное пространство).
TF-IDF же напрямую ловит точное лексическое пересечение (общее название
препарата, дозировку, форму выпуска) — ровно то, что отличает
«тот же товар» от «просто похожая категория», без всякого обучения.

**Оба сигнала слабые в абсолютном выражении** (AP ~0.15-0.17 против базы
0.073 — лифт всего ×2, не ×5-10). Это тоже содержательный результат:
Аптека — самая сложная категория не просто по низкому pos_rate, а потому
что её негативы **уже лексически похожи** на позитивы (общая
фармацевтическая лексика: «таблетки», «мг», «капсулы» и т.п.) — дешёвый
лексический майнинг тут наловит в основном лёгких негативов, для по-настоящему
трудных нужен сигнал посильнее (сама модель, точное сравнение атрибутов).

**Следующий шаг** (не запущено): как только будет готов кэш BERTA
(`../berta-lora-pair-cache`), подтянуть её false positives и посмотреть,
концентрируются ли они у высокого ft/tfidf cosine — это подтвердило бы
(или опровергло) гипотезу, что BERTA путается ровно там же, где путается
голая лексика. Плюс стоит прогнать тот же пилот на паре других категорий
(например «Электроника», «Ювелирные изделия») — Аптека может быть не
показательна для всех 20.
