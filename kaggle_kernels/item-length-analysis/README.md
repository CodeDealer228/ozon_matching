# item-length-analysis

Сколько информации мы теряем на обрезке текстовых полей товара
(`name` 128 / `category` 64 / `attributes` 384 / `combined` 640 симв.)?

- **Kaggle:** https://www.kaggle.com/code/maxamsecret/item-length-analysis
- **Тип:** script · **GPU:** нет (CPU) · **интернет:** выкл

## Суть
Считает распределение **необрезанных** длин каждого поля (децили) по всему
каталогу `items.parquet` (13.4M строк) и долю строк, которые режутся текущими
лимитами. Lazy/streaming-скан без материализации полного текста, GPU не нужен —
специально чтобы гонять параллельно с GPU-обучением, не отъедая квоту.

## Что использовалось
- **Датасет:** `maxamsecret/ozon-ecup-2026-matching` (`items.parquet`).

## Результат (`output/run1_clean.log`), 13 397 761 товар
| Поле | лимит | mean | доля обрезанных |
|---|---|---|---|
| `name` | 128 | 55.3 | **3.03%** |
| `category` | 64 | 13.7 | 0.00% |
| `attributes` | 384 | 439.8 | **47.38%** |
| `combined` | 640 | 538.7 | **28.45%** |

Вывод: лимит `category` избыточен, `name` почти не режется, а вот **384 симв.
на `attributes` рубит почти половину товаров** и ~28% товаров упираются в 640.
Аргумент в пользу пересмотра лимитов / более длинного контекста (актуально для
выбора bi-encoder'а — см. [`../giga3b-quantize-benchmark`](../giga3b-quantize-benchmark)).
