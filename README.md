# Ozon E-CUP 2026 — Сопоставление товаров

Классификация дублей пар товаров для хакатона Ozon Tech E-CUP 2026
(контейнерное соревнование — retrieval уже сделан организаторами, этот
репозиторий — только этап попарной классификации/ре-ранжирования).

Проект прошёл несколько архитектурных итераций: от baseline-кроссэнкодера
через LoRA-дообучение к нескольким параллельно исследуемым направлениям —
более крупные энкодеры (BERTA, FRIDA, Giga-3B) и bi-encoder на
Qwen3-Embedding. Актуальный лучший результат на реальном тестовом стенде —
у BERTA cross-encoder + LoRA, дообученной на TPU с `PAIR_MAX_LENGTH=256`
(см. таблицу ниже).

Подробности (точная формула препроцессинга, определение метрики, особенности
железа, полная история экспериментов) — в **[CLAUDE.md](CLAUDE.md)**: этот
README — быстрый старт и карта репозитория, CLAUDE.md — полный референс,
`reports/experiment_log.md` — сырая хронология с разбором багов.

**На проверке (тест ещё не снят):** `tpu_human_llm_best_176_5120` — тот же
`frida-llm-tpu-sft` continue-SFT прогон, но чекпоинт с более ранним шагом
(`global_step=5177`) и более высоким val (0.7060 против 0.6753 у `hour08`
выше) — сохранён потому что улучшил `best_val` на момент своего чекпоинта, а
не по времени на часах. Val выше не гарантирует тест выше (проект уже видел
оба направления — см. пункт про `ecup_qwen_stage2_submit` ниже) — числа
нужны с реального стенда. **Мердж-источник для `frida-percat-lora` держится
на паузе** (см. `kaggle_kernels/frida-percat-lora/kernel-metadata.json`,
сейчас всё ещё указывает на человеко-only epoch4/0.7660) до результата этой
и, возможно, ещё одной проверки — прямое указание, не гадаем заранее.

`?` — val для этого конкретного сабмита не зафиксирован ни в одном отчёте
проекта (не значит «не измерялся», значит «число не найдено при аудите» —
если найдётся, дополнить). FRIDA-строки делят один val (0.7660/0.7602) —
это буквально одни и те же веса, обслуженные на разных `PAIR_MAX_LENGTH`.

Два наблюдения, которые пока остаются гипотезами (не подтверждены
контролируемым сравнением):
- **Рост `PAIR_MAX_LENGTH` 128→256, похоже, поднимает тест-скор** —
  `matching-berta_tpu_lora-submit` (256, 0.47) заметно обгоняет
  `berta_catboost` (128, 0.40), хотя это не чистый A/B (разные чекпоинты
  BERTA, разные головы). Правда, у `berta_catboost_256_len` подъём
  `PAIR_MAX_LENGTH` до 256 **не помог** — но там сама BERTA обучалась на
  128, а здесь у BERTA-TPU-чекпоинта тренировка и инференс совпадают по
  длине (256/256), что и должно быть решающим фактором, а не сама цифра.
- **`ecup_qwen_stage2_submit`** — чекпоинт, который просел на val (~1%)
  относительно предыдущего, но вырос на тесте — намекало на "переобучение
  под train помогает тесту". Пара `matching-berta_tpu_lora-submit` /
  `berta_tpu_lora_after_llm` этот паттерн **не повторяет**: там просадка и
  на val, и на тесте идут в одну сторону — обычная, ожидаемая корреляция.
  То есть эффект из qwen-случая не выглядит универсальным правилом, скорее
  специфичен для того конкретного чекпоинта/архитектуры — требует больше
  точек данных, прежде чем на него полагаться.
- **FRIDA переносится на тест заметно хуже BERTA при сопоставимом val —
  подтверждено теперь на чистой паре без устаревшей метрики.**
  `tpu_human_160_epoch4_5120_batch`: val **0.7660** (реально измерен на этих
  весах, не унаследован) → тест **0.4069**. BERTA-TPU-чекпоинт: val 0.7087 →
  тест **0.47**. FRIDA обгоняет по val на 0.057, но проигрывает по тесту на
  0.063 — тот же качественный паттерн, что и в исходном (более слабом,
  stale-val) сравнении ниже, но теперь на настоящих числах с обеих сторон.
  FRIDA всё ещё в 6.4 раза больше по параметрам (823M против 128.3M).
  Известное различие, которое это может объяснять (не разделено
  экспериментом): BERTA дообучалась на `matches_llm.parquet`+human
  вперемешку, а этот FRIDA-чекпоинт — только на human; устраняется в
  `kaggle_kernels/frida-llm-tpu-sft` (см. ниже, ещё не сабмитился).

  Исходное (более слабое) сравнение, для истории:
  `Frida Lora V2 Epoch`: val ≈0.69 → тест **0.386**. Val отличается на ~0.02,
  тест — на 0.084.

  **Важная оговорка про «val ≈0.69» у этого сабмита: это число никогда не
  измерялось на его весах.** В `train_state.json` чекпоинта лежит
  `{"global_step": 1127, "best_macro_pr_auc": 0.6937681383971788}`, а
  0.69376813… — это в точности скор `frida-lora-checkpoint-v1-best`, с
  которого прогон резюмился. «Тихий» save по wall-clock записал
  унаследованный running-best вместо метрики собственных весов, а лог кернела
  вернулся нулевого размера — та же ловушка со stale-метрикой, что разобрана в
  `reports/berta_tpu_lora_provenance/`. Реальный val меряется в
  `kaggle_kernels/frida-validate-checkpoint`; веса сабмита и датасета
  `maximmarkovbb/frida-lora-v2-epoch-last` совпадают побайтово по **обеим**
  половинам модели — `adapter_model.safetensors` (sha256 `6914cbb181b9c014…`)
  и `classifier.pt` (`75b4ce886c67555a…`), так что мерить есть что и ничего
  не додумывается.

  **Третья, самая конкретная гипотеза про 0.386 — рассинхрон препроцессинга
  train/inference.** `frida-lora-v2-epoch` обучался на кэше
  `frida-tokenize-items-v2-cache`, чья политика парсит JSON атрибутов и
  выносит длинные/https/oem-значения в конец **до** обрезки по 384 символам.
  Сабмит так не делает: `submits/frida/lora_v2_epoch/frida_lora/src/utils.py`
  режет сырую нераспарсенную строку атрибутов, то есть подаёт v1-порядок. До
  модели доезжают буквально другие символы. Это не рассуждение о
  генерализации, а измеримая величина — валидатор теперь считает один и тот же
  чекпоинт на обоих кэшах, и разрыв между строками и есть цена рассинхрона.

### Check пройден, но Public — ещё нет (2026-08-20, в работе)

Хронология четырёх реальных прогонов на судейском стенде, каждый менял
переменные относительно предыдущего известного состояния:

| Прогон | Что менялось | Результат |
|---|---|---|
| `frida_human_256len_16k_batch` | фикс. `batch_size=1024→16384`, без probe | **Check упал**, ~3 мин |
| исходный `frida_tpu_human_256_epoch4` (с GPU batch-size probe) | добавлен probe (doubling+binary search до реального forward pass) | **Check упал**, ~2 мин |
| `frida_tpu_human_256_epoch4_200k_tokenizing_chunk` | `TOKENIZE_CHUNK_SIZE=20_000→200_000` (10×) | **Check упал**, менее 3 мин |
| `frida_tpu_human_192_epoch4_200k_tokenizing_chunk` | ветка от **уже исправленной** (после фикса ниже) версии `frida_tpu_human_256_epoch4`: `pair_len`/`item_len` 256→192, `tokenizing_chunk`=200k | **Check прошёл впервые**, упал на **Public** через 5-10 мин (бюджет Public ~6 мин) |

Первые три прогона выявили: дело не в `batch_size`, не в probe и не в
размере чанка токенизации — на Check-стадии (~1000 пар / ~2000 items)
токенизация/reorder/сборка пар тривиально быстры независимо от этих
констант, а падение указывало на **фиксированные накладные расходы
старта**, не масштабирующиеся с числом пар. Исправление: загрузка весов
модели переведена в фоновый поток (`threading.Thread`), параллельно с
загрузкой/reorder текста и токенизацией на главном потоке — раньше всё шло
строго последовательно, хотя токенизации нужен только токенайзер (грузится
отдельно и быстро), а не полные веса. GPU batch-size probe убран (грузил
несколько реальных forward pass'ов оверхеда перед тем, как реальные пары
вообще касались GPU) — заменён на аналитическую оценку потолка по
arithmetic активаций (не измерение, честная формула и допущения в коде).

**Четвёртый прогон — первый, где Check вообще пройден.** Но он одновременно
менял и длину (256→192), и уже включал фикс с фоновой загрузкой — то есть
**не чистый A/B**: неизвестно, прошёл ли Check благодаря укороченной длине,
благодаря фикс-у оверлапа, или благодаря обоим факторам сразу. Учитывая, что
на Check-масштабе (~1000 пар) разница между 192 и 256 токенами в самой
токенизации/сборке пар пренебрежимо мала, а вот фикс оверлапа устраняет
ровно то фиксированное накладное на старте, что раньше валило Check —
**более вероятное объяснение: Check-проблема решена фиксом с потоком**, а
не длиной. Не подтверждено экспериментом — следующий кандидат для
изоляции: прогнать 256-длину с уже применённым фиксом оверлапа отдельно.

**Новый, более узкий бутылочный горлышко: Public-стадия по времени
компьюта.** На 192-длине реальное время (5-10 мин) превысило бюджет Public
(~6 мин) — совпадает с более ранней FLOPs-оценкой в этом файле: GPU-компьют
растёт примерно линейно с `PAIR_MAX_LENGTH`, и даже 192 (не говоря о 256)
может не укладываться в бюджет на чистом компьюте, без всякого
CPU-оверхеда. Кандидаты на следующий шаг: (а) изолированный тест
256-длины с уже применённым оверлап-фиксом — закрыть вопрос про Check;
(б) реальный CPU/GPU оверлап на инференсе (готовить следующий батч на CPU,
пока GPU считает текущий — тот же паттерн, что уже сработал для загрузки
модели, но применённый к циклу инференса) — снижает Public/Private-время,
но не Check (там оверлапить почти нечего из-за маленького масштаба);
(в) дальнейшее снижение `PAIR_MAX_LENGTH`, ценой части качества, которую
эта длина и была призвана вернуть.

**Пятый прогон (`tpu_human_192_epoch4_14k_chunk`, фикс. `batch_size=8192`
без всякого расчёта) впервые дал полный traceback вместо таймаута —
`ModuleNotFoundError: No module named 'peft'` в фоновом потоке загрузки
весов, хотя офлайн-установка на главном потоке отчиталась об успехе.**
Корень — не гонка потоков (`sys.path` общий на процесс, потоки его видят
одинаково), а классическая ловушка `sys.path_importer_cache`: новая
«тихая» версия `maybe_offline_install` добавляла `target_dir` в `sys.path`
**до** того, как директория вообще создана (это нужно для быстрой проверки
«пакет уже стоит с прошлой стадии»), пробный `import peft` на пустой
директории закономерно падал — но Python кеширует это «здесь ничего нет»
на уровне пути и не перечитывает директорию сам, даже когда `pip` реально
кладёт туда файлы мгновением позже в том же процессе. Первый же `import
peft` где угодно ещё в этом процессе (здесь — в фоновом потоке) видел
кэш, а не диск. В старой версии (`tpu_human_256_epoch4`) этого бага нет:
там `sys.path.append` шёл ровно один раз, уже после успешной установки, so
путь никогда не бывал в кэше пустым. Фикс — `importlib.invalidate_caches()`
сразу после успешного `pip install`, перед возвратом из функции.
Воспроизведено локально с нуля (не полагаясь на то, что `peft` уже стоит в
venv — чистый фейковый пакет, тот же сценарий: добавить путь → упавший
`import` → создать директорию с реальным модулем → `import` без
`invalidate_caches()` падает тем же классом ошибки → с `invalidate_caches()`
проходит). Пересобранный `matching-tpu_human_192_epoch4_14k_chunk-submit.zip`
проверен: `run.py` в корне архива, фикс на месте, веса
(`adapter_model.safetensors`, `classifier.pt`) побайтово те же, что у
`tpu_human_256_epoch4` (val 0.7660) — меняется только длина обслуживания.

**Побочная находка из этого же лога, не связанная с крашем:**
`os.cpu_count()` на реальном стенде вернул **240**, не 20 из CLAUDE.md.
Предыдущая правка (`OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`RAYON_NUM_THREADS`
32→20, обоснованная именно спецификой CLAUDE.md) в свете этого факта могла
пойти не в ту сторону — не убрала оверсабскрайб, а наоборот срезала
доступный параллелизм на порядок. Пока не тронуто, требует отдельного
изолированного прогона.

**Шестой прогон (тот же сабмит, уже с фиксом выше) дошёл до Public
(114,235 пар) и упал в первую же минуту с уже настоящим traceback:**
`BlockingIOError: [Errno 11] Resource temporarily unavailable` внутри
`multiprocessing.Pool(n_workers).__init__` → `os.fork()`. Причина — прямое
следствие находки про 240 «ядер» выше: `n_workers = os.cpu_count() or 1`
в `_load_needed_item_texts` пытался форкнуть 240 процессов разом
(`multiprocessing.pool._repopulate_pool_static`), а число CPU и число
разрешённых процессов в контейнере — **разные, не связанные лимиты**
(`cpu.max`/`cpuset` против `pids.max`/`RLIMIT_NPROC`); `os.cpu_count()`
ничего не говорит о втором. Реальный контейнер здесь оказался ограничен
существенно ниже 240.

Фикс — не подбор меньшей константы (это была бы ещё одна догадка против
неизмеренного реального потолка, и поиск этого потолка перебором стоил бы
больше сабмитов, чем экономия того стоит), а **полное удаление
`multiprocessing.Pool`** из `_load_needed_item_texts`: reorder атрибутов
теперь всегда однопоточный. Реальная цена по уже измеренной скорости
(~52K items/сек локально): на масштабе этого самого прогона (223,536
items) — **~4.3 секунды**. Тот же баг (тот же паттерн `os.cpu_count()` +
`multiprocessing.Pool`) был во всех остальных живых FRIDA-сабмитах —
`tpu_human_256_epoch4`, `tpu_human_256_epoch2`, `tpu_human_224_epoch4_14k_chunk`,
`tpu_human_192_epoch4_200k_chunk` — и, вероятно, объясняет задним числом
непонятный обрыв лога у `224_epoch4_14k_chunk` без traceback ранее в этом
же разделе: реальный traceback, скорее всего, шёл сразу за той точкой, где
лог оборвался. Фикс применён во всех пяти файлах одинаково; zip
пересобран и перепроверен только для `tpu_human_192_epoch4_14k_chunk`
(активный кандидат на сабмит), остальные четыре ждут пересборки по
запросу перед следующей попыткой на них.

**Восьмой прогон (`batch_size=8192`, `PAIR_MAX_LENGTH=192`, уже с
исправлениями выше) дошёл до настоящего forward pass на Public и упал в
VRAM OOM — честная, информативная ошибка:**

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 27.00 GiB.
GPU 0 has a total capacity of 79.19 GiB of which 26.53 GiB is free.
Process has 52.65 GiB memory in use (51.69 GiB allocated by PyTorch).
```

Реальная потребность на `(batch=8192, seq=192)` = 52.65 + 27.00 = **79.65
GiB** — превышение всего на ~0.46 GiB, не в разы.

**Упавшие 27.00 GiB — не загадка, а точно идентифицируемая величина.**
`eager`-реализация внимания T5 считает softmax-матрицу
attention-вероятностей в **fp32** (стандартная практика для численной
стабильности), форма `(batch, num_heads=24, seq, seq)`:

```
8192 × 24 × 192 × 192 × 4 байта = 27.00 GiB  — ТОЧНОЕ совпадение с логом
```

Проверено прямым вычислением, совпадает с числом из лога до заявленной
точности. Это единственное слагаемое во всём forward pass, растущее как
`seq²`, а не как `seq` — все остальные веса/активации (Q/K/V/O-проекции,
gated FFN, hidden states, LoRA-дельты) растут линейно по `batch×seq`, плюс
фиксированная часть (веса модели ~1.65GB bf16 + CUDA-контекст ~1GB, вместе
~2.5 GiB). Раскладка 79.65 GiB: `attn_probs=27.00` (точно) + `fixed≈2.5` +
`остальное≈50.15` (линейное по `batch×seq`, получено вычитанием).

Собраны два варианта на этой основе: `tpu_human_192_epoch4_6912_batch`
(тот же `seq=192`, `batch=6912`) и `tpu_human_160_epoch4_8192_batch`
(тот же `batch=8192`, `seq=160`) — по модели выше оба должны были иметь
запас ~12-16 GiB.

**Девятый прогон (`tpu_human_192_epoch4_6912_batch`) опроверг эту модель.**
Упал с бóльшим, а не меньшим дефицитом:

```
Tried to allocate 22.78 GiB. GPU 0 has 79.19 GiB total, 11.61 GiB free.
Process has 67.57 GiB memory in use (66.65 GiB allocated by PyTorch).
```

`attn_probs(6912,192) = 6912×24×192×192×4 байта = 22.78 GiB` — снова точное
совпадение, формула для этого слагаемого подтверждена дважды подряд. Но
«уже занято» выросло до **67.57 GiB** против 52.65 GiB при **бо́льшем**
батче 8192 — итоговая потребность 90.35 GiB, заметно больше, чем
предсказывала линейная по batch модель (~67.2 GiB), и больше, чем даже у
упавшего batch=8192. Меньший батч не обязан требовать меньше памяти в
сумме, если что-то другое растёт вместе с числом итераций цикла.

**Рабочая гипотеза (не подтверждена профилированием, но хорошо
обоснована):** при 114,235 парах `batch=8192` даёт 13 полных батчей +
хвост 7739 строк (94.5% от полного), а `batch=6912` — 16 полных +
хвост 3643 строки (52.7% от полного) — то есть у batch=6912 не только
больше итераций, но и хвостовой батч другой формы, заметно отличающейся
от «стабильной» формы всех предыдущих батчей. Это ровно тот класс
проблемы, что уже разбирался в этом проекте для TPU/XLA (`.claude/skills/
kaggle-experiment-safety`: «a training loop that lets shapes drift... pays
a real compile on every new shape») — только для CUDA аналог не
перекомпиляция, а то, что кэширующий аллокатор PyTorch может держать
зарезервированные блоки под несколько разных форм одновременно вместо
переиспользования одной, раздувая пиковую занятую память сверх того, что
нужно было бы при одной стабильной форме.

**Фикс — паддинг последнего батча до полного `batch_size`** (тем же
приёмом, что уже проверен в `frida_tpu_embed_cache_human.py`: последняя
строка повторяется, реальный результат отбрасывается для «лишних» строк,
на выход идут только настоящие предсказания). Качество не меняется —
те же прогнозы, тот же порядок; меняется только то, что каждый forward
pass в цикле теперь имеет ровно одну и ту же форму. Применено во всех
семи файлах.

**Десятый сабмит — `tpu_human_192_epoch4_5888_batch`** — тот же `seq=192`,
`batch=5888`, уже с паддингом. **VRAM больше не проблема: OOM не случился.**
Прогон дошёл до реального инференса на Public, дошёл и в Private, и упал
там на **7-8 минуте с `Container did not finish in time`, без единой
строки лога.** То есть фикс с фиксированной формой батча сработал именно
так, как и предполагалось — но новое, уже видимое узкое место — не память,
а чистое время на полном объёме Private, ровно та FLOPs-оценка, о которой
шла речь раньше в этом разделе.

**Одиннадцатый сабмит — `tpu_human_192_epoch4_5120_batch`** — дальнейшее
снижение батча, но с новой проблемой: таймаут по времени **не показывает
логи вообще**, в отличие от падения с ненулевым кодом выхода. Значит нужен
другой инструмент — не «уменьшить батч и снова гадать», а **заставить
процесс упасть громко, пока он ещё жив**.

**Двенадцатый прогон — тот же сабмит, но пересобранный с `PYTORCH_ALLOC_CONF=
expandable_segments:True`** (реально применённый в этой сессии, после того
как обнаружился отсутствующим — см. коммит про char-budget rule v2 — на
Check-стадии сначала упал в OOM именно из-за фрагментации, `"9.57 GiB
reserved by PyTorch but unallocated"`; после фикса пересобранный zip дошёл
до реального Public-инференса). Полный лог сохранён:
`reports/frida_diagnostic_runs/5120_batch_192_seqlen_public.log`.

**VRAM больше не проблема, но впритык**: диагностический лог пиковой
памяти на 25,600/114,235 пары (186с от старта пайплайна) показал `77.00
GiB allocated, 78.44 GiB reserved` — **0.75 GiB свободно** из 79.19 GiB
общей ёмкости. `batch=5120/seq=192` технически не падает, но резервировать
больше батч на этой длине уже некуда.

**Реальная, трижды подтверждённая устойчивая скорость: 217.6 пар/с**
(три независимых замера почти совпадают — 217.9, 217.2, 217.6 — без
деградации во времени, чистое steady-state число, не переходный процесс).
Принудительный диагностический `raise` сработал ровно по таймеру (304с
от старта пайплайна, из них ~68.6с — сетап), обработав 51,200/114,235 пар
(44.8%) — подтверждает, что вся конструкция (лог прогресса + лог VRAM +
принудительное падение) работает именно так, как спроектирована.

**Вывод по бюджету времени** (экстраполяция реальной скорости на полный
объём, не измерение — но по трём согласованным точкам, не по одной):

| Стадия | Пар | Бюджет | Прогноз при 217.6 пар/с | Итог |
|---|---|---|---|---|
| Public | 114,235 | 360с (6 мин) | ~594с (сетап ~69с + инференс) | **~1.65× сверх бюджета** |
| Private | ~275,000 | 780с (13 мин) | ~1394с | **~1.79× сверх бюджета** |

`seq=192/batch=5120` — **VRAM-безопасен, но недостаточно быстр** для обеих
стадий, причём Private зажимает жёстче Public (2.84 мс/пару бюджета
против 3.15 мс/пару у Public) — нужный прирост скорости ~1.9-2.0×.
Увеличивать `batch_size` дальше некуда (см. VRAM выше) — единственный
проверенный в этом проекте рычаг такого масштаба прироста — **снижение
`PAIR_MAX_LENGTH`**. Наивная (линейная по длине) оценка даёт ориентир
seq_len≈100-106 для нужного ускорения; реальная зависимость, скорее всего,
даже лучше линейной (attn_probs растёт как seq², не как seq) — то есть
128 может оказаться уже достаточно, но это не измерено на этом же,
пофикшенном пайплайне (все более ранние точки на 128/160/224/256
собраны ДО фиксов fixed-shape-batching и PYTORCH_ALLOC_CONF, не
сравнимы напрямую). **Следующий конкретный шаг**: тот же диагностический
приём (self-timeout + VRAM-лог) на `seq=128, batch=5120` — дёшево (не тратит
дневной лимит сабмитов) и даст вторую реальную точку вместо
экстраполяции с одной.

**Тринадцатый прогон — `tpu_human_128_epoch4_5120_batch` прошёл ВСЕ стадии
реально, тест-скор 0.398.** Наивная линейная оценка (seq≈106-128) оказалась
верной — 128 хватило. Важный побочный вывод: раз обе стадии реально
уложились в бюджет, диагностический self-timeout ни разу не сработал —
`RuntimeError` не бросался, `predict_pipeline` дошёл до конца штатно.

**Найденный по ходу риск, пока не реализовавшийся, но реальный для
бо́льших длин.** `DIAGNOSTIC_FORCE_FAIL_AT_SECONDS=300` — общий порог,
применяемый к КАЖДОЙ стадии независимо (Public и Private — разные
контейнеры, таймер стартует заново). У Public реальный бюджет 360с, у
Private — 780с: `300` лежит МЕЖДУ ними. Если реальное время на более
длинных seq (160, 144 — уже собраны на момент этого разбора) окажется,
скажем, 400-700с на Private — это честный PASS по реальному бюджету, но
диагностика убила бы контейнер раньше и превратила бы его в ложный FAIL,
зря потратив попытку из дневного лимита. На 128 повезло — там реально всё
уместилось до 300с на обеих стадиях, порог не успел показать эту
проблему. **Фикс** (в `160`/`144`, ещё до их первого реального сабмита):
`DIAGNOSTIC_FORCE_FAIL_AT_SECONDS` поднят 300→700 (безопасно ниже
Private-бюджета 780с, оставляет ~80с на запись CSV) — Public-стадия
всё равно упадёт по-настоящему первой на 360с, если не уложится, диагностика
там уже избыточна; смысл диагностики теперь целиком в Private.

**Четырнадцатый прогон — раздвинутый порог (700с) всё равно оказался
ловушкой.** Реальные результаты на ODS для 128/160/176: у всех троих
статус **`Error: Container finished with non-zero exit code`**, но при
этом **реальный Mean PR-AUC посчитан** (0.398/0.4069/0.4087 —
соответствуют ранее сообщённым тест-скорам). Разгадка: у 128/160/176
показывается счёт, но НЕТ кнопки "Показать" (в отличие от
безрезультатных `-` прогонов выше) — платформа, похоже, не даёт посмотреть
лог Private, если Public уже отработал и посчитался. Прямого
подтверждения через UI получить не удалось, но косвенные улики
достаточно сильны: статус `non-zero exit code` — это подпись
КОНТРОЛИРУЕМОГО падения (`raise RuntimeError`), а не платформенного килла
по таймауту (`did not finish in time`, как показывают настоящие
таймауты — см. пример `ecup_qwen_biencoder_submit.zip` в истории команды,
не имеющий отношения к этому диагностическому коду и всё равно
показывающий именно эту, другую строку). А у 128 порог был ещё НЕ
поднят (оставался 300с) — то есть даже раздвинутый до 700с порог мог всё
ещё срабатывать раньше настоящего 780с-лимита Private.

**Фикс: диагностический self-crash (`check_diagnostic_clock`,
`DIAGNOSTIC_VRAM_LOG_AT_SECONDS`/`DIAGNOSTIC_FORCE_FAIL_AT_SECONDS`,
`pipeline_t0`) полностью удалён** из `tpu_human_128/160/176_epoch4_5120_batch`
и `tpu_human_176_epoch2_5120_batch` — оставлен только безобидный
прогресс-лог каждые ~20%. Это были жизнеспособные диагностические
инструменты, пока мы ещё не знали, пройдёт ли конфигурация по времени —
но раз 128/160/176 уже показали реальный Public-скор, самодельный таймер
стал чистым риском: он мог тихо превращать честный PASS на Private в
ложный FAIL, из-за чего сабмит нельзя выбрать финальным (см. чекбокс
"Финал" в таблице решений). Платформенный таймаут теперь единственный
ограничитель.

### Как дёшево профилировать реальный H100-стенд

Наблюдение, сделанное по ходу этого разбора и стоящее того, чтобы
зафиксировать отдельно: **упавший сабмит (`Container finished with
non-zero exit code`) не тратит дневной лимит сабмитов, но его лог —
настоящий, полный, с реального H100**, без искажений и без ограничений
локального CPU-стенда. `Container did not finish in time` (реальный таймаут)
— противоположность: **логов не показывает вообще**, что подтверждено
дважды (5888-batch на Private, а ещё раньше — на Check-стадии). Значит
единственный способ узнать что-либо о прогоне, который рискует не
уложиться в лимит — **самому оборвать его раньше и громко**, до того как
реальный таймаут молча всё скроет.

Реализовано в `tpu_human_192_epoch4_5120_batch` как явно диагностический
сабмит (`run.py` промаркирован, всегда падает намеренно):
- прогресс каждые ~20% строк внутри `_run_inference` (не полный `tqdm` —
  он либо не рендерится в неинтерактивном логе, либо превращается в сотни
  строк, которые вытесняют из усечённого лога самое полезное);
- один лог пиковой VRAM (`torch.cuda.max_memory_allocated()`/
  `max_memory_reserved()`) примерно через 3 минуты **от старта
  `predict_pipeline`**, не от старта инференса;
- принудительный `raise` примерно через 5 минут — конвертирует потенциальный
  тихий таймаут в громкое, залогированное падение с полной сводкой
  (сколько пар обработано, с какой скоростью).

Все три часа/константы (`PROGRESS_LOG_FRACTION`, `DIAGNOSTIC_VRAM_LOG_AT_SECONDS`,
`DIAGNOSTIC_FORCE_FAIL_AT_SECONDS`) — открытые числа в `src/utils.py`, можно
подстроить под конкретный вопрос. Реальный способ получить точные тайминги/
память с судейского стенда без затрат дневного лимита сабмитов — используйте
целенаправленно, когда нужно измерить что-то конкретное про реальный стенд.

### `frida-llm-tpu-sft` (LLM+human, рецепт BERTA): val просел после первого часа и не восстановился

`kaggle_kernels/frida-llm-tpu-sft` резюмировал лучший human-only чекпоинт
(0.7660) и обучался на `matches_llm.parquet`+human вперемешку,
`PAIR_MAX_LENGTH=256`, с новой `MultiLayerHead` (1024, 256) вместо
одиночного `nn.Linear`. Сессия дошла до `CANCEL_ACKNOWLEDGED` на ~8 часах
(9 чекпоинтов — `best` + `checkpoint_hour01`…`08`, каждый с честным,
реально измеренным `val_macro_pr_auc`, не наследуемым — контракт
чекпоинтов из `.claude/skills/kaggle-experiment-safety` соблюдён):

| Чекпоинт | step | val |
|---|---|---|
| **best / hour01** | 5,177 | **0.7060** ← пик, сразу после 10%-warmup |
| hour02 | 8,650 | 0.7004 |
| hour03 | 12,966 | **0.6530** ← провал, −0.053 от пика |
| hour04 | 16,525 | 0.6656 |
| hour05 | 20,081 | 0.6717 |
| hour06 | 23,611 | 0.6739 |
| hour07 | 27,374 | 0.6741 |
| hour08 | 31,093 | 0.6754 |

Val резко просел сразу после первого часа и **ни разу не вернулся** к
пиковому значению за оставшиеся ~7 часов — медленно отползает вверх, но
даже на `hour08` всё ещё на 0.031 ниже пика. Тот же паттерн, что уже бил
проект на MiniLM continue-SFT (`LR=4e-4` без достаточного warmup — просадка
ниже стартовой точки без восстановления; см. «Continued LoRA SFT» в
`reports/experiment_log.md`). Правдоподобное объяснение: чекпоинт `best`
снят на шаге 5177 — сразу по выходу из 10%-warmup, пока LoRA+голова ещё

унаследованное качество human-only чекпоинта. Дальше LLM-микс на ещё
достаточно высоком LR его расшатывает, и восстановление идёт медленно —
не доказано напрямую (нет отдельного профилирования), но согласуется с
арифметикой: по проекции `PROJECTED_ROWS_PER_SEC=120` косинус-расписание
было рассчитано на ~28,687 шагов, а прогон дошёл до 31,093 — то есть
последние ~2,400 шагов (весь `hour08`) уже шли на полу `LR_MIN_RATIO=0.05`
от пика, что и объясняет, почему подъём к концу настолько пологий.

собственный докстринг): резюмированный чекпоинт обучался на **v2**-кэше
атрибутов, а этот прогон использует **v1** для обеих частей (human+LLM),
поскольку v2-кэша для LLM-скоупа не существует — реальный кандидат на
дополнительную причину просадки, не изолирован от эффекта самого LLM-микса.

Оба крайних чекпоинта (`best`, `hour08`) собраны как сабмиты
(`submits/frida/tpu_human_llm_best_176_5120`,
`submits/frida/tpu_human_llm_hour08_176_5120`) на уже проверенном
`PAIR_MAX_LENGTH=176`/`BATCH_SIZE_FIXED=5120` (реально прошедшем ODS на
human-only линии, тест 0.4087) — та же логика «best vs last», что уже
применялась для BERTA/Qwen: непонятно заранее, снижает ли качество
train/serve-рассинхрон v1/v2-кэша и незавершённый LR-анниллинг сильнее,
чем помогает более широкое покрытие LLM-данными.

### Throughput на H100: что можно поднять без потери качества (или почти без)

**Самый очевидный рычаг — переключить `attn_implementation` на `"sdpa"` —
уже пробовали и отклонили по веской причине.** В истории проекта
(`kaggle_kernels/frida-lora-sft-human-only-10-epochs`) `sdpa` дал **100%
шагов NaN** на этой же модели: fused CUDA-кернелы
`scaled_dot_product_attention` имеют задокументированные NaN-баги с
padding-масками на bf16/fp16, особенно (но не только) на более старых
архитектурах вроде T4. `eager` стоит намеренно, не по недосмотру. Трогать
это без отдельного контролируемого теста — реальный риск скатиться не в
«чуть хуже качество», а в «сломанные предсказания».

Что безопаснее и стоит сделать:

1. **`PYTORCH_ALLOC_CONF=expandable_segments:True`** — прямая рекомендация
   из самого текста ошибки PyTorch. **Применено** во всех девяти
   FRIDA-сабмитах (после того как обнаружилось отсутствующим вообще везде
   — потерялось при CRLF-чистке в этой же сессии). Первое реальное
   подтверждение полезности — `5120_batch`'s собственный Check-краш
   показал `"9.57 GiB reserved by PyTorch but unallocated"` (крупная
   величина, в отличие от двух более ранних крашей с 306.73/266.48 MiB) —
   после фикса тот же сабмит дошёл до Public без единого OOM (см.
   «Двенадцатый прогон» выше).
2. **Фикс с фиксированной формой батча выше** — уже применён, ждёт
   проверки на 10-м сабмите.
3. **Динамический паддинг по батчам вместо фиксированного `PAIR_MAX_LENGTH`
   для каждой пары.** Сейчас каждая пара паддится до полного
   `PAIR_MAX_LENGTH`, даже если её реальное содержимое короче — то есть и
   память, и FLOPs тратятся на чистый паддинг. Если отсортировать пары по
   реальной длине и паддить каждый батч только до максимума **внутри
   батча**, а не до глобальной константы — большинство батчей станут
   короче среднего, что снижает и память, и компьют, и (что важнее всего)
   потенциально позволяет вернуться к полным 256 токенам (как училась
   модель) для тех пар, которым это реально нужно, оставаясь дёшево для
   всех остальных. Качество не меняется вообще (реальные предсказания на
   непаддинговых позициях идентичны). Самый сильный кандидат по
   соотношению польза/риск для качества — но и самый трудоёмкий
   (сортировка/группировка/восстановление исходного порядка строк — ровно
   тот класс правки, что уже дважды в этой сессии давал реальный баг при
   спешке). Не реализовано, кандидат на отдельный, тщательно
   протестированный заход.
4. **`torch.compile()`** — теоретически реальный прирост (fusion
   кернелов), но добавляет компиляцию при первом вызове — ровно тот класс
   стартового оверхеда, что уже валил Check-стадию в этом проекте
   несколько раз подряд. Стоит тестировать изолированно, не как первую
   попытку.
5. **int8-квантизация замороженной базы** — у проекта есть прецедент почти
   бесплатной int8-квантизации (Giga3B, 0.4004→0.3973 val, «nearly free»),
   но это другая модель; для FRIDA такого измерения нет. Реальная, но
   отдельная и пока не начатая проверка.

### FRIDA: chars/token и где реально режутся атрибуты (2026-08-20)

Впервые измерено напрямую (раньше только предполагалось по аналогии с
MiniLM): FRIDA-токенайзер даёт **~3.12 chars/token** на реальном каталоге
(против 1.33 у английского WordPiece MiniLM). По полям (10k items,
`items_human.parquet`) — `attributes` съедает **76% токен-бюджета**
(mean 95.8 из 126.9 токенов на пару полей), `category` — доли токена.
Сырые (без обрезки) длины полей показывают, откуда растёт эта цифра:
`attributes` на p70 уже длиннее текущего лимита `MAX_ATTR_CHARS=384`
(523 символа), на p99 — в 4.5 раза длиннее (1731). `name`/`category`
обрезаются заметно меньше. Полный разбор, методология и обе таблицы —
`reports/frida_char_token_analysis.md`.

**Найденный и исправленный баг: символьный бюджет обрезки не был
пересчитан под 256-токенный режим FRIDA.** `MAX_NAME_CHARS,
MAX_CATEGORY_CHARS, MAX_ATTR_CHARS = 128, 64, 384` — формула из CLAUDE.md,
рассчитанная под 128-токенный MiniLM-кроссэнкодер — была скопирована
байт-в-байт (комментарий в коде прямо говорил `byte-matches CLAUDE.md`) во
все кэш-строящие кернелы FRIDA с `max_length=256`, ни разу не
пересчитанная под новый токенный потолок. Эффект: `category` получала
64 символа (~27 токенов по её собственному chars/token=2.34) при реальном
максимуме **8 токенов** — избыточный, впустую потраченный бюджет; а
`attributes` получала 384 символа (~130 токенов) при реальном p90=136,
p99=151, max=227 токенов — то есть символьная обрезка резала реальный
контент атрибутов **до** того, как токенайзер вообще успевал его увидеть,
хотя итоговый токенный потолок 256 почти никогда не был узким местом
(реальный максимум объединённого текста пары полей — 248 токенов).

**Досадная оплошность в первой попытке фикса.** Первая правка (в этой же
сессии) пересчитала бюджет всего по 10k-item Kaggle-сэмплу с интерполяцией
процентилей на глаз (`MAX_NAME_CHARS=156` из «p99=50 ток. × 2.83 + запас
10%» — p99 самого по себе не было в отчёте, только p90/p99 с округлением
между ними): `156/28/564`. Рабочая, но заведомо грубее, чем оправдано —
точный процентиль был в одном локальном скрипте от готовности
(`items_human.parquet`, 214MB, лежит в `data/` целиком, точный расчёт по
всем 711,304 items — секунды, не Kaggle-кернел). Пересчитано по полному
датасету и заменено на точные значения без интерполяции.

**Итоговое правило (по прямому запросу): `MAX_NAME_CHARS`/`MAX_CATEGORY_CHARS`
не должны зависеть от `max_seq_len` вообще** — требования «95-99% name
влезает целиком» и «100% category влезает целиком» задаются самим
распределением полей, а не токен-бюджетом. От `max_seq_len` зависит только
остаток, отдаваемый под `attributes`:

```python
NAME_CHAR_TARGET = 140      # p98=137 (точно, весь датасет) + запас -> ~98.1% name без обрезки
CATEGORY_CHAR_TARGET = 32   # реальный max=23 по всем 20 категориям + запас -> 100%

def derive_char_budgets(max_seq_len, chars_per_token, overhead_tokens=15):
    name_tok = ceil(NAME_CHAR_TARGET / chars_per_token["name"])
    cat_tok  = ceil(CATEGORY_CHAR_TARGET / chars_per_token["category"])
    attr_tok = max_seq_len - overhead_tokens - name_tok - cat_tok
    return NAME_CHAR_TARGET, CATEGORY_CHAR_TARGET, floor(attr_tok * chars_per_token["attributes"])
```

`overhead_tokens=15` — реально измеренная (не предположенная) стоимость
литералов `paraphrase: Name:  Category:  Attributes: ` + спецтокены,
совпала для FRIDA и BERTA. chars/token — свои для каждого токенайзера
(измерены напрямую, не по аналогии): FRIDA (`RobertaTokenizer`, byte-BPE,
vocab 93,651) — name=2.847, category=2.343, attributes=2.994; BERTA
(`BertTokenizer`, WordPiece, vocab 55,083) — name=2.783, category=2.612,
attributes=**2.500** (заметно менее эффективен на атрибутах, чем FRIDA).

При `ITEM_MAX_LENGTH=256` (текущий выбор для кэшей обеих архитектур) это
даёт `NAME=140, CATEGORY=32, MAX_ATTR_CHARS=529` (FRIDA) / `442` (BERTA) —
заменено в источнике **пяти** кэш-строящих кернелов: `frida-tokenize-items-v2`
(кэш, на котором обучен текущий лучший FRIDA-чекпоинт, val 0.7660),
`frida-tokenize-items-human`/`frida-tokenize-items-llm` (v1-кэши), более
раннем `frida-tokenize-items`, и **впервые найденный тот же баг** в
`berta-tokenize-llm-256` (BERTA использует ту же item-level архитектуру
кэша, что и FRIDA — тот же `128/64/384`, ни разу не тронутый до этого).
Значения для `max_seq_len=128/192` — та же формула, другой остаток под
attributes (146/122 при 128, 338/282 при 192 для FRIDA/BERTA
соответственно) — не строятся отдельными кэшами: item-кэш на 256
покрывает как донор для любого последующего `PAIR_MAX_LENGTH` через
fair-share truncation на уровне пары, строить три версии item-кэша не
нужно.

**Правка — только для будущей пересборки кэша**, ничего в уже обученных
весах или в инференс-контракте текущего задеплоенного сабмита не менялось:
сейчас идущий `frida-llm-tpu-sft` (резюмирует чекпоинт 0.7660) уже
стартовал с готовым, ещё не пересчитанным кэшем — решение оставить его
доучиваться как есть, а не прерывать ради ещё не пересобранного кэша (см.
`reports/experiment_log.md` для полного разбора и цифр).

### ⚠️ LLM-разметка используется САБСЕМПЛОМ, а не целиком

**Важно при чтении любых результатов новых обучений (2026-08-21 и позже):
они получены НЕ на всех 11,187,780 LLM-парах, а на выборке.** Формулировка
«обучено на human + LLM» без уточнения — неверная; правильная — «human +
LLM-сабсемпл».

Причина — арифметика квоты, не осторожность. Измеренная скорость проекта
(`frida-tpu-human-sft`, FRIDA 823M, 8 ядер TPU) — **120 строк/с** на
`PAIR_MAX_LENGTH=256`; собственный докстринг `frida-llm-tpu-sft` фиксирует:
«*Against 11,480,303 mixed rows a full epoch needs ~26.5 hours*». На
`seq=192` получается ~170 строк/с, и полный LLM всё равно даёт **~19ч** для
20 LoRA и **~74ч** для 3 эпох полного SFT — против квоты **20ч/неделю на
аккаунт, 9ч на сессию**.

**Как именно собирается выборка** (одинаково в обоих кернелах,
`stratified_llm_sample`, `seed=42`):

1. **Категории балансируются поровну** — фиксированная квота на каждую из 20
   категорий, а не пропорционально её доле. Это совпадает с метрикой:
   macro-PR-AUC считает все категории равнозначными.
2. **Внутри категории — стратификация по значению таргета**, сохраняющая
   естественное распределение этой категории.
3. Если у категории строк меньше квоты — берутся все.
4. Реализованные счётчики (по категориям и по уровням таргета) пишутся в
   `llm_subsample_report.json` в выводе кернела — выборка воспроизводима и
   проверяема, а не «доверьтесь seed».

**Отдельная находка: LLM-таргеты не непрерывные, а 10 дискретных значений
`k/9`** — то есть счёт голосов 9 судей, а не вероятность:

| target | доля | target | доля |
|---|---|---|---|
| 0.000 (0/9) | **64.22%** | 0.556 | 2.41% |
| 0.111 | 0.01% | 0.667 | 1.52% |
| 0.222 | 5.65% | 0.778 | 2.47% |
| 0.333 | 4.44% | 0.889 | 6.08% |
| 0.444 | 2.26% | 1.000 (9/9) | **10.94%** |

**Фильтр по уверенности рассматривался и отклонён.** «Уверенные» строки
(`≤0.2` или `≥0.8`) — уже **81.25%** данных естественным образом, так что
фильтр поднял бы долю всего с 81% до 100%, выбросив те **18.75%**, что лежат
ближе всего к границе решения — а PR-AUC это ранжирование, оно решается
именно там. Вдобавок мерджится **human-only** чекпоинт
(`frida-tpu-human-sft`, 4 эпохи human-only), то есть специалисты — первый
контакт модели с LLM-разметкой вообще, и показывать ей только лёгкие случаи
— худший возможный момент.

### Известное ограничение: мало данных без лика для головы поверх BERTA

`berta_catboost_top_final` (CatBoost на 768 сырых эмбеддингах BERTA +
classifier_score + tf-idf + category) вышел **хуже** чистого классификатора
на тесте (0.457 против 0.47), хотя на val было наоборот (0.7467 против
0.7087). `get_feature_importance()` показал причину: 96.11% важности — на
768 сырых измерениях эмбеддинга, размазанных почти плоско (максимум
отдельного измерения 0.43%), а сам `classifier_score` — та единственная
фича, которая одна даёт 0.47 на тесте — получил только 1.9%. Классическое
переобучение: слишком много фич на слишком малом числе строк.

**Почему строк так мало.** Топ-чекпоинт BERTA (`berta-tpu-lora-top-checkpoint`)
обучался на человеческом **train**-сплите (`matches.parquet`, 292,523 строки,
80%) вместе с `matches_llm.parquet`. Значит для головы поверх его
эмбеддингов без лика годится только **val**-сплит — 73,131 строка (20%),
дальше делённая 80/20 на train/val самого catboost → всего 58,504 строки
на обучение catboost. Этого хватает для одной-двух признаков, но не для
771 (768 эмбеддинга + 3). `matches_llm.parquet` мог бы дать на порядок
больше данных, но качество LLM-разметки хуже человеческой и распределение
другое (полностью непересекающийся с `matches.parquet` набор товаров — 0
общих id, см. CLAUDE.md → "Данные") — просто подмешать её нельзя, нужна
отдельная проверка.

**Частичный фикс** — `berta_catboost_pca32`: PCA(32) на эмбеддинге вместо
768 сырых измерений + усиленная регуляризация (`depth` 8→6, `l2_leaf_reg`
15→30). Важность `classifier_score` выросла до 19.3% (в 10 раз), val почти
не просел (0.7419 против 0.7467), тест подрос до 0.469 — но всё ещё чуть
ниже 0.47. Проблема нехватки данных смягчена, но не решена полностью.

**Следующий шаг (в проработке)**: закэшировать эмбеддинги на **всей**
человеческой разметке (все 365,654 пар, не только val-срез), используя
чекпоинт, который для этих конкретных пар не участвовал в обучении —
кандидат: `kaggle_kernels/berta-tpu-human-continue-384` (дообучен уже
после топ-чекпоинта на human-only данных). Дальше — многослойная голова
поверх зафиксированных эмбеддингов (архитектура ещё не выбрана), с
промежуточным слоем как потенциальной фичей для CatBoost. Кэширующий
кернел под это уже подготовлен (`kaggle_kernels/berta-embed-cache-all-human`),
но пока не запущен — ждём подтверждения, что `berta-tpu-human-continue-384`
действительно даёт прирост качества.

Исторически первый работающий сабмит — LoRA-дообученный
`cross-encoder/ms-marco-MiniLM-L-12-v2` (`submits/minilm/lora/`):

| Вариант | macro PR-AUC (val) | Mean PR-AUC (лидерборд) |
|---|---|---|
| Baseline (frozen encoder + LogReg) | 0.3710 | 0.1333 |
| LoRA SFT | 0.5282 | 0.265 |

## Архитектуры

Коротко, что перепробовано (детали и обоснование выбора — в CLAUDE.md):

- **`submits/minilm/lora`** — исходный baseline: `cross-encoder/ms-marco-MiniLM-L-12-v2`
  (33M) + LoRA SFT на `matches.parquet`. Отправная точка проекта.
- **BERTA** (`sergeyzh/BERTA`, 128.3M, дистиллят FRIDA в BERT-форме) —
  LoRA-дообученный cross-encoder, с несколькими вариантами головы: линейная
  (`submits/probes/berta`, `submits/berta/tpu_lora`) и CatBoost поверх
  эмбеддингов (`submits/berta/catboost`, `submits/berta/catboost_256_len`).
  Обучающие кернелы: `kaggle_kernels/berta-lora-sft*`, `berta-merge-lora`,
  `berta-catboost-*`, `berta-llm-tpu-sft` (полномасштабный SFT на TPU
  v5e-8 поверх `matches_llm.parquet`).
- **FRIDA** (`ai-forever/FRIDA`, 823M, T5-энкодер) — bi-encoder,
  LoRA-дообученный. Выбран как более дешёвая альтернатива для
  пере-токенизации (item-level кэш вместо per-pair). Кернелы:
  `kaggle_kernels/frida-tokenize-items*`, `frida-lora-sft*`,
  `frida-lora-continue-2ep`, `frida-lora-v2-epoch` (актуальная версия —
  тайм-аут-устойчивые чекпоинты, новая политика упорядочивания атрибутов).
  Сабмит: `submits/frida/lora_v2_epoch`, `submits/frida/tpu_human_256_epoch4`,
  `submits/probes/frida`.
- **Giga-Embeddings-instruct** (3.45B, `giga3b_probe`) — проба
  bi-encoder-подхода на ещё большем энкодере; zero-shot cosine similarity
  уже бьёт обученный baseline, но candidate-пары почти не переиспользуют
  товары, так что bi-encoder-выигрыш ("encode once, compare many") не
  реализуется — по FLOPs не укладывается в лимиты судейского стенда.
  Запаркован, см. `reports/experiment_log.md`.
- **`omarelshehy/arabic-english-sts-matryoshka`** (~560M, `matryoshka_probe`) —
  проба "насколько крупный энкодер потянет H100-стенд" в схеме
  baseline-архитектуры (frozen encoder → CLS → LogReg).
- **Qwen3-Embedding-0.6B bi-encoder** (`submits/qwen/stage2`,
  `ecup_qwen_biencoder_submit_128_length`, `matching-qwen-berta-catboost-submit`) —
  LoRA + MLP/CatBoost голова поверх эмбеддингов. **Текущий лучший результат
  проекта на реальном тесте.**

## Данные (не в git, слишком тяжёлые)

| Файл | Размер | Для чего |
|---|---|---|
| `matches.parquet` | 4MB | 365K пар с человеческой разметкой — train/val |
| `items_human.parquet` | 214MB | Каждый товар, на который ссылается `matches.parquet` — **используйте это для локальной разработки/тестов**, а не полный `items.parquet` |
| `matches_llm.parquet` | 104MB | 11.19M пар с LLM-разметкой (слабые/мягкие метки, непрерывные 0..1) — вторая стадия continued LoRA SFT |
| `items.parquet` | 4.1GB | Полный каталог товаров (13M+ строк) — нужен только для полномасштабного прогона |

### Вариант A: прямая ссылка (без Kaggle-аккаунта)

Организаторский bucket на Yandex Cloud, публичный, без креденшлов:

```bash
python scripts/download_data.py                              # все 4 файла в data/
python scripts/download_data.py matches.parquet items_human.parquet   # только нужные
python scripts/download_data.py --overwrite items.parquet     # перекачать заново
```

Скрипт пропускает файл, если он уже лежит в `data/` (кроме `--overwrite`), и
пишет во временный `*.parquet.part`, атомарно переименовывая по завершении —
битый файл в `data/` не останется, даже если скачивание прервётся.

### Вариант B: Kaggle-датасет

Все данные соревнования также лежат в **[maxamsecret/ozon-ecup-2026-matching](https://www.kaggle.com/datasets/maxamsecret/ozon-ecup-2026-matching)** (приватный — нужен доступ):

```bash
mkdir -p data
# Только то, что нужно для локальной разработки (matches.parquet + items_human.parquet):
kaggle datasets download maxamsecret/ozon-ecup-2026-matching -f matches.parquet -p data
kaggle datasets download maxamsecret/ozon-ecup-2026-matching -f items_human.parquet -p data
# Всё целиком, включая items.parquet на 4.1GB:
kaggle datasets download -d maxamsecret/ozon-ecup-2026-matching -p data --unzip
```

Веса моделей публикуются как отдельные Kaggle-датасеты по мере обучения
(смёрженные LoRA-веса, PEFT-адаптеры, item-token-кэши) — полный список
источник/потребитель по каждому кернелу в `kaggle_kernels/README.md`.

## Пересборка и тестирование сабмита

Паттерн одинаков для любого `submits/<name>/` (конкретные шаги сборки весов
отличаются по архитектуре — см. README/докстринг соответствующего
`kaggle_kernels/*`):

```bash
python scripts/build_submission_zip.py --submission-dir submits/<name>
python scripts/test_submission.py --submission-dir submits/<name> --n-pairs 1000
```

`test_submission.py` собирает небольшой реальный сэмпл из
`data/items_human.parquet` + `data/matches.parquet` и запускает `run.py`
через тот же CLI-контракт, что использует судейский харнесс, проверяя формат
вывода, совпадение числа строк и детерминизм. **Всегда также распаковывайте
собранный zip в чистую папку и тестируйте именно его** (а не просто папку
`submits/<name>/`) — баги упаковки (обёрточная папка в zip, пакет, которого
нет в судейском Docker-образе) проявляются только на реальном архиве.

Для LoRA-сабмита (`submits/minilm/lora`) есть отдельный шаг мёржа адаптера:
```bash
python scripts/merge_lora.py                # LoRA-адаптер -> смёрженные веса
```

## Ограничения соревнования, кратко

Полный разбор — в CLAUDE.md, здесь только самые острые углы:

- Судится **офлайн**, в фиксированном Docker-образе
  (`odsai/ecup26-matching-baseline:1.0` по умолчанию) — код может
  импортировать только пакеты, которые реально есть в этом образе
  (`numpy`, `pandas`+`pyarrow`, `torch`, `transformers`; **никакого**
  `polars` — узнали это из упавшего сабмита).
- Железо: 1x H100 80GB, 20 CPU, 200GB RAM.
- 3 отдельных лимита по времени, не один общий бюджет: Check 1 мин
  (1000 пар), Public 6 мин (~115K пар), Private 13 мин (~275K пар).
- **5 сабмитов в день, жёсткий лимит.** Тестируйте локально + на Kaggle GPU
  dry-run прежде чем тратить попытку.
