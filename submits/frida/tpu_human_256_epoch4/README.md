# FRIDA + LoRA, 4 эпохи human-only на TPU (`PAIR_MAX_LENGTH=256`)

**Статус: тест-стенд ещё не пройден.** Три реальных прогона подряд падали на
Check-стадии (`Error: Container did not finish in time`, 1 мин / 1000 пар) —
подробный разбор и хронология в главном [README.md](../../../README.md) →
«Check-стадия падает». В этой директории — последняя версия кода с
исправлениями тайминга (фоновая загрузка весов модели, аналитический
батч-сайз вместо probe, поднятые лимиты чанков/потоков); ещё не
подтверждена на стенде.

Val macro PR-AUC чекпоинта — **0.7660**, лучший val во всём проекте
(предыдущий рекорд 0.7551 у BERTA-384). Соседняя директория
[`../tpu_human_256_epoch2`](../tpu_human_256_epoch2) — тот же прогон,
чекпоинт эпохи 2 (val 0.7602), собран как проверка гипотезы «меньше
human-only эпох лучше переносится на тест» (та же гипотеза, что объясняет
просадку BERTA-384 c ростом числа эпох, см. `berta/human_continue_384/`).

## Что это за решение

Cross-encoder: `ai-forever/FRIDA` (T5EncoderModel, 823M параметров, CLS-пулинг
с позиции 0) + LoRA-адаптер (не смёржен — веса грузятся раздельно из-за
5GB-лимита архива) + линейный классификатор поверх pooled-представления.

## Гиперпараметры обучения

Обучено кернелом `kaggle_kernels/frida-tpu-human-sft` (TPU v5e-8), резюм с
чекпоинта `maximmarkovbb/frida-lora-checkpoint-v1-best` (val 0.69377):

| Параметр | Значение |
|---|---|
| LoRA | `r=16, alpha=32, dropout=0.10`, `target_modules=["q","k","v","o","wi_0","wi_1","wo"]` (реальные имена модулей T5, не BERT) |
| LR | `3e-4`, warmup 10%, cosine |
| Батч | `PER_CORE_TRAIN_BATCH=16`, `PER_CORE_EVAL_BATCH=32`, 8 TPU-ядер → эффективный train-батч 128 |
| Данные | только `matches.parquet` (human), без `matches_llm.parquet` — канонический seed-42 сплит (292,523 train / 73,131 val) |
| Эпохи | план 4, все 4 прошли за одну TPU-сессию |
| `PAIR_MAX_LENGTH` | **256** (единственное намеренное отличие от предыдущих FRIDA-чекпоинтов — 128 обрезал ~94% реальных пар) |
| `ITEM_MAX_LENGTH` | 256 (кэп на один item внутри пары) |

## Логика обрезки текста item'а (важно: byte-match с обучением)

Формула символьной обрезки **не** совпадает с формулой из корня CLAUDE.md
(та — для MiniLM/BERTA). У FRIDA два слоя обрезки:

**1. Символьный слой** (до токенизации), с v2-политикой порядка атрибутов:

```
MAX_NAME_CHARS, MAX_CATEGORY_CHARS, MAX_ATTR_CHARS = 128, 64, 384
MAX_ITEM_CHARS = 128 + 64 + 384 + 64  # = 640
PREFIX = "paraphrase: "
```

Атрибуты — не сырая обрезка JSON-строки. Сначала парсится JSON, атрибуты
**переупорядочиваются** (правила применяются последовательно, поздние
перекрывают ранние — реализовано как один ранг со стабильной сортировкой):

1. значение длиннее 200 символов → в конец
2. значение содержит `"https"` → ещё дальше в конец
3. `"oem"` в ключе или значении → в самый конец

Ре-сериализованный JSON (`json.dumps(..., ensure_ascii=False)`) режется по
`MAX_ATTR_CHARS` **после** переупорядочивания — иначе `json.loads` получил
бы невалидный обрубленный JSON, а решение "что выживет после среза" как раз
и есть смысл политики. `variant_shuffled` (5%-й аугментационный вариант с
перемешанным порядком атрибутов) используется только на обучении, не на
инференсе.

Текст товара: `f"Name: {name} Category: {category} Attributes: {attr_ordered}"[:640]`.

**2. Токенный слой**: item целиком токенизируется (bos…eos), затем span
`Category: …` вырезается по паттерну BPE-токенов (категория одинакова у
обеих сторон пары — ноль дискриминативного сигнала, чистая трата бюджета).
Пара собирается fair-share truncation'ом (`allocate_pair_budget`) до
`PAIR_MAX_LENGTH=256`: сторона короче половины бюджета не обрезается,
освободившееся место уходит другой стороне.

Это НЕ рефакторинг ради красоты — предыдущий FRIDA-сабмит
(`../lora_v2_epoch`, тест 0.386) кормил модель **сырыми** атрибутами без
v2-переупорядочивания, хотя чекпоинт обучался на переупорядоченных. До
модели буквально доезжали другие символы почти на каждом товаре (проверено:
политика меняет текст у 99.99% товаров из 20K реальных). Один из кандидатов
на объяснение слабого 0.386.

## Провенанс: последовательность кернелов и Kaggle-датасетов

```
ai-forever/FRIDA (базовая модель, HF)
  │
  ▼
kaggle_kernels/frida-tokenize-items-v2 (CPU)          — item-кэш с v2-политикой атрибутов
  → датасет maximmarkovbb/frida-tokenize-items-v2-cache
    (711,304 items, max_length=256, variant_base + variant_shuffled)
  │
  ▼
kaggle_kernels/frida-lora-continue-2ep (1×T4)          — 2 полные эпохи human-only, best-only чекпоинты
  → val 0.69377 (25% прогресса до отмены)
  → датасет maximmarkovbb/frida-lora-checkpoint-v1-best (с optimizer-state)
  │
  ▼
kaggle_kernels/frida-tpu-human-sft (TPU v5e-8)         — резюм с v1-best, PAIR_MAX_LENGTH 128→256, 4 эпохи
  → val: 0.7437 (эп.1) → 0.7602 (эп.2) → 0.7657 (эп.3) → 0.7660 (эп.4)
  → чекпоинты checkpoint_epoch01..04 + best (все сохранены отдельными директориями)
```

Полная хронология и обоснование каждого решения — `kaggle_kernels/README.md`
→ раздел «FRIDA», и корневой `README.md` → «Check-стадия падает».
