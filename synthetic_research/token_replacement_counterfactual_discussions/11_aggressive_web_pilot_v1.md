# Агрессивный web-пилот v1

## Цель

Сравнить базовый метод Макса с более дорогой генерацией на одних и тех же
2 000 human-train positive-парах. Результаты двух потоков не смешиваются до
отдельного обучения и оценки.

## Общий source pack

Локальный source pack строится round-robin по всем 20 категориям из полного
dry-run базового pipeline. Он содержит только ссылки на исходные локальные пары,
категорию и предложенные токены. Validation источником не является.

Файлы после подготовки:

- `artifacts/token_replacement_counterfactual/comparison_pilot_v1/comparison_source_pack.jsonl`;
- `artifacts/token_replacement_counterfactual/comparison_pilot_v1/comparison_source_pack_manifest.json`.

## Arm A: baseline

Для каждого источника один генератор получает исходную пару, `offered_tokens` и
три few-shot-примера категории. Он выбирает до двух замен либо `skip` через
structured output. Это ровно метод из `10_max_baseline_rotation_pipeline.md`.

## Arm B: aggressive web

### 1. Три независимых генератора

Одна и та же пара обрабатывается тремя ролями:

1. `catalog`: проверяет тип значения и внутреннюю согласованность карточки;
2. `hard-negative`: ищет замену, максимально похожую внешне, но меняющую товар;
3. `marketplace`: предпочитает естественные значения из реальных объявлений.

У ролей разные system prompts и небольшие различия temperature. Все они могут
выбирать `source_token` только из `offered_tokens` и могут вернуть `skip`.

### 2. Голосование

Одинаковая операция `source_token -> replacement_token`, предложенная минимум
двумя генераторами, попадает в shortlist. Единогласный `skip` сразу завершает
источник. Простое большинство не считается окончательным ответом: оно лишь
сокращает набор для валидатора.

### 3. Web research по необходимости

Поиск вызывается, если генераторы расходятся либо операция меняет бренд,
модель, артикул или код совместимости. В поиск уходят только:

- категория;
- локально извлечённая краткая подсказка типа товара;
- один исходный токен;
- предполагаемый смысловой тип токена.

Полные карточки, ID, target и validation в поисковый запрос не попадают.
Используются Alibaba built-in `web_search` и `web_extractor`; отдельный search
API key не нужен. Контракт уже реализован в
`scripts/token_replacement_web_search_tool.py`.

### 4. Отдельный валидатор

Валидатор видит исходную пару, предложения генераторов и короткие web-evidence.
Он может выбрать только операцию из shortlist/research-кандидатов либо вернуть
`skip`. Локальная проверка затем подтверждает буквальную применимость замены к
обеим карточкам.

### 5. Материализация

Для каждой принятой операции создаются те же две пары, что в baseline:

- обе карточки изменены — `target=1`;
- изменена одна карточка — `target=0`.

Так меняется качество выбора замены, но не правило построения обучающих данных.

## Честное сравнение

Для Arm A и Arm B фиксируются одинаковые source pack, split, исходная модель и
training recipe. Сравниваются:

- доля `skip` и принятых операций;
- доля ручных ошибок на стратифицированной выборке;
- стоимость и время на одну принятую операцию;
- macro/micro PR-AUC после отдельного одинакового дообучения;
- per-category изменение относительно control без синтетики.

Основной gate — улучшение относительно baseline-arm, а не просто высокий процент
принятых текстов.

## Текущее состояние

Код web research и строгий контракт готовы. Первый baseline-проход исчерпал
прежний реестр до 35B без inference и списания токенов. После этого пользователь
разрешил все подходящие модели Alibaba Singapore; Max/Plus/Flash и большие
open-weight модели добавлены отдельным расширением и проверяются следующим
запуском. API-часть aggressive pilot использует тот же расширенный реестр.
