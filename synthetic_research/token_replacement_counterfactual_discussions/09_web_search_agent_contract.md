# Web-search агент: контракт инструмента и prompt v1

## Почему отдельный research-этап

Если дать генератору свободно ходить в интернет и сразу редактировать пару, сложно понять, что именно он нашёл и почему выбрал замену. Поэтому поиск отделяется от финального решения:

1. `research`: найти реальные кандидаты и доказательства;
2. `decision`: выбрать один из кандидатов для конкретной пары через строгий structured output;
3. `materialize`: локально применить замену и построить positive/negative группу.

Alibaba Singapore уже предоставляет built-in `web_search` и `web_extractor` в Responses API. Новый внешний search key для первого эксперимента не требуется.

## Вход research-инструмента

```json
{
  "category": "Бытовая техника",
  "product_type_hint": "робот-пылесос",
  "source_token": "xiaomi",
  "semantic_type_hint": "brand",
  "max_candidates": 5
}
```

В интернет не отправляются ID, label, validation, полные приватные карточки и полный список атрибутов. `product_type_hint` извлекается локально или выбирается генератором до поискового вызова.

## Выход research-инструмента

```json
{
  "status": "found",
  "semantic_type": "brand",
  "queries": ["бренды производители роботов-пылесосов"],
  "candidates": [
    {
      "replacement_token": "dreame",
      "reason": "бренд выпускает тот же тип товара",
      "evidence": [
        {
          "url": "https://example.org/product",
          "title": "Product page",
          "claim": "страница показывает робот-пылесос бренда Dreame"
        }
      ]
    }
  ],
  "skip_reason": ""
}
```

Допустим и `status=skip`, если надёжного кандидата нет.

## System prompt для research-модели

```text
Ты — исследователь реальных товарных значений для контрфактуальной генерации
marketplace-пар. Твоя задача — найти в открытом интернете правдоподобные замены
одного токена, не редактируя исходную пару и не решая за финальный генератор.

Правила:
1. Сначала установи смысловой тип source_token: brand, model, article,
   size_or_quantity, compatibility_code или other.
2. Замена обязана сохранять смысловой тип. Бренд меняется на бренд, модель на
   модель, артикул на артикул сопоставимого формата.
3. Кандидат должен реально относиться к product_type_hint. Например, бренд
   должен действительно выпускать этот тип товара, а не просто существовать.
4. Предпочитай официальные страницы производителя, каталоги и крупные
   marketplace/retailer pages. Для сильного кандидата достаточно одной
   официальной страницы либо двух независимых товарных страниц.
5. Не предлагай алиас, другую транслитерацию или вариант регистра source_token.
6. Не придумывай факты. Если доказательств нет или тип токена неясен, верни skip.
7. replacement_token — один токен без пробелов, пригодный для буквальной замены.
8. Выполни только узкие поисковые запросы по классу товара и типу значения.
   Не ищи исходную приватную карточку целиком.
9. Верни только валидный JSON указанного контракта. Сохрани URL, title и короткое
   собственное изложение доказательства; не копируй длинные фрагменты страниц.
```

## Prompt финального decision-generator

```text
Ты создаёшь независимые контрфактуальные операции для пары одинаковых товаров.
Исходный source_token можно выбрать только из offered_tokens. Для каждого токена
research_candidates содержит найденные в интернете значения и доказательства.

Выбери замену, которая:
- сохраняет смысловой тип токена;
- естественно выглядит во всех местах обеих карточек;
- при применении к обоим item создаёт новый positive;
- при применении только к одному item делает пару negative;
- не требует менять другие несвязанные факты.

Не обязан использовать найденный кандидат. Если доказательство слабое,
replacement ломает внутреннюю согласованность или безопасной операции нет,
верни skip. Не создавай replacement_token вне research_candidates. Ответ — только
вызов submit_replacement_decision по переданной JSON Schema.
```

## Поисковая стратегия

Для brand:

- `"<product_type_hint>" бренды производители`;
- `site:официальный-домен <brand> <product_type_hint>` после нахождения кандидата.

Для model/article:

- искать товарные страницы того же типа и извлекать модель/артикул только из заголовка или structured product fields;
- не использовать случайные похожие буквенно-цифровые строки;
- формат кандидата должен быть сопоставим с исходным токеном.

Для size/quantity:

- поиск нужен только когда допустимые значения зависят от реального товарного ряда;
- иначе лучше генерировать локально из ограниченного числового контракта.

## Журналирование

На каждый вызов сохраняются:

- hash безопасного research input;
- model snapshot;
- фактические queries;
- URL и claims;
- raw response отдельно;
- нормализованный research JSON;
- token usage и provider request id;
- связь с `source_pair_sha256` только локально, не внутри поискового запроса.

Результаты поиска меняются со временем, поэтому URL, дата и model snapshot являются частью identity эксперимента.
