# Разбор вариантов и рекомендуемая последовательность

## Краткий вывод

Первый рабочий эксперимент следует сделать как `генератор → детерминированные проверки → независимый семантический валидатор`. Голосование и поиск полезны как следующие варианты, но не должны блокировать быстрый baseline.

## Вариант 1: генератор и валидатор

Это рекомендуемая первая архитектура:

1. эвристика формирует конечный список допустимых исходных токенов;
2. генератор выбирает операцию или `skip`;
3. локальный код проверяет JSON Schema, принадлежность токена списку и правильность применения;
4. независимый валидатор проверяет естественность, внутреннюю согласованность и метку;
5. сохраняются решение каждого этапа и причина отказа.

Валидатор не должен молча исправлять кандидата. Он принимает или отклоняет его, чтобы provenance оставался однозначным.

## Вариант 2: три генератора и голосование

Голосовать за свободно сгенерированные строки неэффективно: три модели могут предложить три одинаково хорошие, но разные замены. Большинство не возникнет.

Голосование становится корректным, если генераторы выбирают `operation_id` из общего конечного списка. Например, эвристика заранее предлагает:

```text
op_1: dht11 -> dht22
op_2: esp-01 -> esp-32
op_3: skip
```

Тогда три независимых вызова выбирают один из одинаковых вариантов, и правило `2 из 3` имеет смысл. Альтернатива — несколько генераторов создают кандидатов, а отдельные judges оценивают объединённый список.

Минус варианта — примерно тройная стоимость. Его нужно сравнивать с одиночным генератором на одном и том же небольшом source-наборе.

## Вариант 3: агент и поиск

Поиск способен повысить фактическую корректность, но создаёт дополнительные проблемы:

- результаты меняются со временем и сложнее воспроизводятся;
- сайты могут быть недоступны;
- нужно сохранять URL, дату и извлечённое доказательство;
- стоимость и задержка возрастают;
- поиск не устраняет необходимость локальной проверки.

Рекомендуемая замена живому поиску на первой итерации — каталог реальных значений из canonical human-train. Для каждого сочетания `category + тип товара + ключ атрибута` можно собрать встречавшиеся бренды, модели, размеры и артикулы. Генератор выбирает конечное значение только из этого каталога. Например, бренды пылесосов извлекаются из реальных train-карточек с типом «пылесос», а не придумываются моделью.

Живой поиск можно оставить для аудита небольшого числа сложных случаев, если train-каталог не даёт подходящих значений.

## Qwen3.8 Flash на Kaggle TPU

Нужно различать две модели:

- `Qwen3.8-Flash` — управляемая облачная версия;
- `Qwen/Qwen3.8-Flash-Next` — опубликованные открытые веса.

По официальной карточке открытая модель содержит 125B параметров с 6B активных, дополнительно 51B параметров n-gram embedding и 4B MTP. Малое число активных параметров уменьшает вычисления, но не отменяет хранение весов. BF16-представление значительно превышает память обычного Kaggle TPU v3-8; 4-bit теоретически уменьшает размер, но добавляет риск несовместимости новой архитектуры, квантования и PyTorch/XLA.

Официальные инструкции показывают GPU-serving через Transformers, vLLM и SGLang, но не подтверждают готовый TPU-путь. Поэтому Flash-Next нельзя считать быстрым безопасным вариантом без отдельного минимального compatibility probe. Для первого pipeline практичнее API или меньшая открытая модель; TPU probe не должен блокировать генерацию.

## Более полезные творческие варианты

1. **Каталог типизированных замен.** Конечные значения берутся из train-пула той же категории и типа атрибута.
2. **Симметричная тройка.** Для одной операции создавать `positive both`, `negative left` и `negative right`, чтобы модель не запоминала сторону изменения.
3. **Сложность операции.** Отдельно измерять артикулы/модели, размеры/объёмы, бренды/совместимость и давать им разные веса.
4. **Frequency matching.** Новое значение выбирать сопоставимой частоты, чтобы редкость токена не стала подсказкой класса.
5. **Групповой training contract.** Исходная пара и все её мутации всегда остаются в одной train-группе и получают общий `source_pair_sha256`.
6. **Soft quality weight.** Прошедшие строгие проверки примеры получают больший вес, спорные не обязательно удаляются, а получают меньший вес и отдельный флаг.

## Быстрый план сравнения

1. Закончить human few-shot pack.
2. На одном небольшом наборе источников запустить одиночный generator-validator baseline.
3. На тех же источниках проверить вариант с конечным train-derived replacement catalog.
4. Только если качество остаётся неоднозначным, добавить `2 из 3` голосование.
5. Agent+search и локальный Flash-Next TPU рассматривать как отдельные эксперименты, не как обязательную инфраструктуру.
