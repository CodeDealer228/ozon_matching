# Pipeline: A2 + C Synthetic Hard Negatives for BERTA

По итогу процесс строится как **две независимые ветки синтетики — A2 и C — с общим research-этапом**, а потом отдельно сравнивается их влияние на BERTA. Ключевая идея: validation используется, чтобы понять **на чем модель ошибается**, но synthetic train строится только из train.

1. **Сначала анализируем ошибки текущей BERTA на validation.** Берем файл Гриши со всеми FP/FN и смотрим только четыре худшие категории: `Обувь`, `Ювелирные изделия`, `Одежда`, `Автотовары`. Нас в первую очередь интересуют FP: `label=0`, а BERTA дала высокий score, то есть разные товары показались модели одинаковыми. FN используются как контрпримеры: они помогают не объявить какой-нибудь размер/цвет критическим различием, если реальные positive-пары тоже могут по нему отличаться. Параллельно отделяем ошибки, где BERTA действительно увидела различие, от ошибок, где важная информация просто была отрезана truncation.

2. **Codex строит taxonomy ошибок.** Например, мы можем обнаружить не глобальное правило `разный размер = negative`, а гораздо более узкие failure modes:

   ```text
   Автотовары / фильтры:
   почти одинаковые товары, но разные OEM-коды
   → BERTA часто дает FP

   Ювелирка / конкретный subtype:
   практически одинаковые name, но разные артикулы
   → BERTA часто дает FP
   ```

   При этом что-то вроде `разный размер обуви` может оказаться плохим правилом, потому что среди positive/FN будет много таких же различий.

3. **После этого validation больше не используется для генерации.** Мы берем найденные failure patterns и ищем **аналогичные случаи в human train**. Это принципиально важно: нельзя взять конкретный FP из validation, нагенерить из него обучающих примеров, а потом честно считать качество на том же validation.

4. **Ветка A2: усложняем реальные train-negative пары.** Находим в train пару `(A, B)` с `label=0`, желательно похожую на один из обнаруженных validation failure modes. Qwen получает оба товара, но ему запрещено менять идентичность `B`. Его задача — сделать `B → B'`, сохранив все факты B, но переписав описание так, чтобы оно стало лексически/стилистически больше похоже на A. На первом эксперименте лучше оставить `attributes` неизменными и разрешить менять только `name`.

   Например:

   ```text
   A:
   "Фильтр масляный MANN W914/2 для Lada"

   B:
   "Масляный фильтр Mahle OC384 ВАЗ"

   B':
   "Фильтр масляный Mahle OC384 для ВАЗ"
   ```

   `Mahle`, `OC384`, совместимость и остальные факты не меняются.

   Затем **до обучения** прогоняем старую BERTA:

   ```text
   old_score = BERTA(A, B)
   new_score = BERTA(A, B')

   hardening_delta = new_score - old_score
   ```

   Если `new_score > old_score`, synthetic действительно сделал negative более сложным для нашей модели. Если score не вырос — такой пример можно вообще не использовать.

5. **Ветка C: воспроизводим реальные минимальные различия.** Из train ищем near-identical negative-пары, соответствующие найденным failure patterns:

   ```text
   A ≈ B
   label = 0
   существенное различие = конкретная semantic characteristic
   ```

   Здесь Qwen не должен сам придумывать правило. Data определяет:

   ```text
   что менять
   +
   желательно на какое значение менять
   ```

   Например, из реальных train-товаров выяснилось, что в конкретном product family встречаются подтвержденные negatives `60Ah` vs `70Ah`. Тогда для другого подходящего товара код может поставить задачу:

   ```text
   semantic_attribute = capacity
   old = 60Ah
   new = 70Ah
   ```

   А Qwen занимается только корректным созданием synthetic item.

6. **Для C Qwen обязан синхронизировать все representations характеристики.** Если значение присутствует одновременно в `name` и `attributes`, меняются оба:

   ```text
   original:
   name = "... 60Ah ..."
   attributes.capacity = "60 А·ч"

   synthetic:
   name = "... 70Ah ..."
   attributes.capacity = "70 А·ч"
   ```

   При этом все остальные semantic characteristics должны остаться прежними. После ответа идет deterministic validator: проверка `name ↔ attributes`, отсутствия дополнительных изменений, дублей, изменения category и т. д. Сомнительные generation просто отбрасываются.

7. **A2 и C сохраняем как разные датасеты.** Не смешиваем их сразу:

   ```text
   train_baseline

   train + SYN_A2

   train + SYN_C

   позже:
   train + SYN_A2 + SYN_C
   ```

   Тогда будет понятно, что реально приносит прирост.

8. **Переобучаем одинаковую BERTA и оцениваем только на untouched human validation.** Для каждого запуска фиксируем одинаковые hyperparameters, seed и validation. Смотрим прежде всего AP по четырем проблемным категориям, но обязательно также общий macro AP и остальные категории. Иначе можно случайно поднять `Обувь`, испортив десять других категорий.

Весь flow:

```text
            CURRENT BERTA
                  │
                  ▼
       validation FP + FN dataset
                  │
                  ▼
        failure-mode research
       + truncation separation
                  │
                  ▼
       taxonomy реальных ошибок
                  │
            НЕ ГЕНЕРИРУЕМ
        ИЗ VALIDATION ITEMS
                  │
                  ▼
          HUMAN TRAIN ONLY
             /          \
            /            \
           ▼              ▼
          A2               C
   real negative     minimal-negative
      A,B              patterns
       │                   │
       ▼                   ▼
 Qwen rewrites B     data chooses mutation
 without changing    + replacement
 its identity              │
       │                   ▼
       │              Qwen applies it
       ▼              consistently
 validator                │
       │                   ▼
       ▼               validator
 BERTA old/new score       │
       │                   │
       ▼                   ▼
 keep true hard       accepted C
 negatives            synthetics
        \                 /
         \               /
          ▼             ▼
        separate training experiments
                  │
                  ▼
          SAME untouched VAL
                  │
                  ▼
      per-category AP + macro AP
```

Причем **первый цикл стоит сделать небольшим**. Не 4000 примеров сразу. Сначала Codex делает taxonomy, потом условно по 50–100 A2 и C candidates на категорию. Смотрим руками примеры, rejection rate и `hardening_delta`. Если качество хорошее — масштабируем до 1000/category.

Это даст ответ не только «помогла ли синтетика», но и **какой именно способ синтетики лечит реальные ошибки BERTA**.
