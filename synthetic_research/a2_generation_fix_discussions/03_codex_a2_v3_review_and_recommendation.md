# Codex: review и рекомендуемый вариант A2 v3

Дата: 2026-08-24  
Статус: design review, без реализации и платных запусков

## 1. Общий вывод

Предложение A2 v3 в целом правильное. Главная идея — вынести извлечение и
проверку фактов в локальный детерминированный код, а Qwen оставить только
ограниченное редактирование названия — существенно безопаснее и дешевле
первого pilot.

Рекомендация: **принять A2 v3 с изменениями**, описанными ниже.

Ключевые изменения к предложению:

- не считать все attributes товара B обязательными для сохранения в его
  названии;
- извлекать из свободного текста только факты высокой уверенности;
- передавать Qwen не просто список разрешённых фактов, а конкретные разрешённые
  операции;
- возвращать два кандидата на пару, а не три;
- не набирать искусственно 30 source pairs, если строгий локальный фильтр даёт
  меньше;
- считать строковую похожесть диагностикой, а не основным критерием качества;
- перед платным pilot добавить локальные regression tests для чисел, единиц,
  размеров, артикулов и кодов моделей.

## 2. Что показала проверка репозитория и A2 source pool

В репозитории уже есть полезная основа для локального анализа:

- `normalize_text`;
- `canonicalize_value`;
- `parse_attributes`;
- `extract_semantics`;
- `find_name_representation`;
- `name_similarity`.

Но текущий семантический слой охватывает только четыре категории: обувь,
ювелирные изделия, одежду и автотовары. Для аксессуаров полноценной схемы пока
нет. Поэтому нельзя объявлять одинаково надёжную семантическую поддержку всех
пяти категорий.

Также найден конкретный дефект текущей числовой проверки:

```text
37-38см  ->  37-38 см
```

может ошибочно классифицироваться как потеря факта `38см`, хотя значение
сохранилось и изменился только пробел перед единицей измерения. До следующего
pilot это нужно закрыть тестом и исправить canonical normalization.

Строгий локальный поиск по 500 A2 source pairs нашёл только 24 пары с сильной
возможностью безопасного hardening: факт присутствует у A, подтверждён
attributes B и пока отсутствует в name B. После дополнительного требования
надёжного negative anchor осталось 11 особенно сильных пар.

Следствие: число `30` не должно быть квотой. Если строгий фильтр даёт 11 или 24
хороших кандидата, нужно запускать их, а не ослаблять правила ради круглого
числа.

## 3. Модель факта

Каждый локально извлечённый факт лучше хранить как типизированную структуру:

```json
{
  "fact_id": "b.attr.brand.pandora",
  "concept": "brand",
  "raw_value": "PANDORA",
  "canonical_value": "pandora",
  "source": "attributes_b",
  "source_key": "Бренд",
  "visible_in_name": false,
  "confidence": "high",
  "identity_sensitivity": "medium"
}
```

Это позволяет валидатору проверять конкретные `fact_id`, сохранять
происхождение каждого факта и по-разному обрабатывать бренд, цвет, размер,
объём и код модели.

## 4. Извлечение и нормализация фактов

### 4.1. Приоритет источников

1. Структурированные attributes — основной источник.
2. Название — источник только для высокоуверенных шаблонов.
3. Fuzzy semantic matching не используется для identity-critical фактов в
   первом pilot v3.

### 4.2. Что можно нормализовать

Безопасные примеры:

- регистр и Unicode;
- повторные пробелы;
- пробел между числом и единицей: `20ml` и `20 ml`;
- заранее проверенные словарные варианты одной единицы или одного значения.

Опасные случаи, которые нельзя склеивать общим fuzzy-правилом:

- ведущие нули в артикулах и кодах;
- произвольные буквенно-цифровые модели;
- размеры шин и составные размерные обозначения;
- количество единиц в комплекте;
- близкие числа с разными единицами;
- конвертация единиц измерения без отдельной проверенной логики.

Для первого pilot лучше не делать межединичную конвертацию.

## 5. Наборы фактов

### 5.1. SAFE_SHARED_FACTS

Факты, подтверждённые и для A, и для B, которые разрешено сделать более явными
в B'. Для первого pilot допускаются exact/canonical совпадение и небольшой
контролируемый словарь эквивалентностей. Fuzzy semantic equivalence остаётся
только сигналом для ручного review.

### 5.2. NEGATIVE_ANCHORS

Факты, подтверждающие, что A и B остаются разными товарами. Anchor разрешён,
только если понятие входит в category-specific whitelist, оба значения
извлечены с высокой уверенностью, они действительно различаются после
canonicalization и понятие имеет достаточную идентификационную силу.

### 5.3. PROTECTED_B_FACTS

Нельзя требовать, чтобы B' содержал все attributes B: исходное название B тоже
не обязано их содержать. Защищать нужно identity-critical факты, уже видимые в
name B, подтверждённые negative anchors, а также числа, размеры, коды и
количества, потеря которых изменит товар.

### 5.4. FORBIDDEN_A_ONLY_FACTS

Это факты, подтверждённые для A, но не подтверждённые для B. Их нельзя
переносить в B'. В автоматический запрет входят только факты высокой
уверенности; сомнительные случаи лучше отправлять в `skip`.

## 6. Локальный opportunity filter

### Tier A

- есть безопасная разрешённая операция;
- есть надёжный negative anchor;
- не обнаружено конфликтов identity.

### Tier B

- есть безопасная разрешённая операция;
- надёжного anchor нет;
- исходная human-negative пара прошла ручную проверку;
- риск переноса identity-critical факта низкий.

### Tier C

Доступна только перестановка слов, удаление шума или поверхностная
нормализация. Такие пары пропускаются без API-вызова.

## 7. A_SAFE_TEMPLATE и ALLOWED_OPERATIONS

Лучше использовать оба механизма одновременно.

`A_SAFE_TEMPLATE` — замаскированное представление A, из которого удалены или
заменены placeholders все A-only identity facts.

`ALLOWED_OPERATIONS` — конкретный список разрешённых изменений:

```json
[
  {
    "operation_id": "op_1",
    "type": "insert_shared_fact",
    "fact_id": "shared.brand.pandora",
    "target": "name2"
  },
  {
    "operation_id": "op_2",
    "type": "move_existing_token_group",
    "token_group_id": "b.material.silver"
  }
]
```

Qwen не решает самостоятельно, какой факт безопасен. Он выбирает и реализует
одну или несколько уже разрешённых операций.

## 8. Контракт ответа Qwen

Модель должна иметь право вернуть `skip`.

```json
{
  "status": "ok",
  "candidates": [
    {
      "name2_prime": "...",
      "used_fact_ids": ["shared.brand.pandora"],
      "applied_operation_ids": ["op_1"]
    },
    {
      "name2_prime": "...",
      "used_fact_ids": ["shared.brand.pandora"],
      "applied_operation_ids": ["op_1", "op_2"]
    }
  ]
}
```

Для pilot достаточно двух кандидатов: это даёт выбор frozen Frida, но не
раздувает completion и не усиливает переоптимизацию под judge-модель.

## 9. Validator v3

Кандидат проходит, только если:

1. JSON и schema валидны.
2. `name2_prime` непустой и отличается от B.
3. Все `used_fact_ids` существуют в локальном contract.
4. Все `applied_operation_ids` были разрешены.
5. Не добавлены FORBIDDEN_A_ONLY_FACTS.
6. Не потеряны PROTECTED_B_FACTS.
7. Сохранены NEGATIVE_ANCHORS.
8. Не появились неподтверждённые числа, размеры, артикулы или коды.
9. Изменение не является одной лишь тривиальной нормализацией.
10. Frozen Frida даёт `hardening_delta > 0`.

Строковая похожесть с A — диагностическая метрика, а не замена проверки фактов
или Frida score.

```text
useful = identity_safe AND negative_safe AND hardening_delta > 0
```

## 10. Frozen Frida

Для каждого безопасного кандидата считаются old score, new score и
`hardening_delta`. Из двух кандидатов сохраняется лучший, но оценки обоих
остаются в артефактах.

Scoring выполняется отдельным дешёвым kernel с тем же preprocessing, что и
baseline Frida. Старый feature cache нельзя использовать для B', потому что
изменённый текст имеет другую identity.

## 11. Few-shot v3

Рекомендуемый набор:

- три успешных примера с полным schema-контрактом;
- три `skip`-примера;
- разные категории и причины отказа;
- пример с опасным A-only числом или кодом;
- пример только с тривиальной нормализацией;
- пример, где нельзя удалять protected fact.

## 12. Минимальный paid pilot

### Бесплатная локальная стадия

1. Прогнать fact extraction по всем 500 source pairs.
2. Построить fact contract, tiers и reject reasons.
3. Провести ручной audit репрезентативной выборки.
4. Исправить normalization и закрыть regression tests.
5. Сформировать immutable generation plan с SHA-256.

### Платная стадия

- максимум 20 source pairs;
- сначала все Tier A;
- остаток — лучшие вручную проверенные Tier B;
- не требовать равного числа по каждой категории;
- один API request на source;
- два candidates на request;
- `thinking=false`;
- автоматические retries выключены;
- один warm-up для измерения cache, затем ограниченный parallel запуск;
- checkpoint и request journal сохраняются до отправки запроса.

Если строгих пар меньше 20, запускается фактическое число, а не ослабляется
фильтр.

### Метрики

- API success rate и `skip` rate;
- доля кандидатов, прошедших schema и safety gates;
- reject reasons;
- доля sources хотя бы с одним полезным вариантом;
- hardening delta: median, p25, p75, maximum;
- результаты по категориям и операциям;
- prompt, completion, reasoning и cached tokens;
- число запросов без полезного результата.

### Safety gate

- ноль критических identity violations в ручной проверке;
- ноль пропущенных forbidden numeric/model transfers;
- положительный hardening delta у достаточной доли принятых sources;
- отсутствие доминирующего ошибочного шаблона;
- стоимость полезного accepted результата лучше первого pilot.

## 13. Стоимость относительно v1

Ожидаемые улучшения:

- локальный filter убирает бесполезные запросы;
- `thinking=false` устраняет основной источник скрытых completion tokens;
- право `skip` уменьшает выдуманные изменения;
- два кандидата используют один общий prompt;
- структурированные операции сокращают свободное рассуждение;
- отсутствие retries защищает от повторной оплаты неизвестных исходов.

Prompt v3 может быть немного длиннее v1 из-за fact contract. Бессмысленный
padding ради cache threshold добавлять не нужно; эффект cache измеряется по
фактическому `cached_tokens`.

## 14. Regression tests до API

- `37-38см` и `37-38 см`;
- `20ml` и `20 ml`;
- ведущие нули;
- `1шт`, `1 шт` и количество в комплекте;
- артикулы и буквенно-цифровые коды;
- размеры шин;
- обозначения вроде `G11`;
- отсутствие переноса числа A в B';
- сохранение protected числа B;
- сохранение negative anchor после перестановки слов.

## 15. Порядок реализации после approval

1. Выделить общий модуль fact contract и canonical normalization.
2. Добавить category-specific whitelist понятий и anchors.
3. Исправить numeric/unit normalization и написать regression tests.
4. Построить локальный A2 v3 plan для всех 500 source pairs.
5. Выполнить ручной audit Tier A/Tier B и зафиксировать manifest.
6. Создать и проверить few-shot v3.
7. Адаптировать generator к операциям, двум candidates и `skip`, сохранив
   безопасный transport profile.
8. Запустить отдельно подтверждённый минимальный paid pilot.
9. Провалидировать кандидаты локально.
10. Посчитать frozen Frida hardening scores отдельно.
11. Пройти quality gate.
12. Только затем согласовать масштаб generation и training run.

## 16. Открытые решения

- допустим ли Tier B или pilot только из Tier A;
- какие понятия являются надёжными negative anchors по категориям;
- достаточно ли двух кандидатов на source;
- какой useful yield требуется для масштабирования;
- какой generation budget разрешён;
- нужно ли отдельно исследовать Accessories.

## 17. Стоп-точка

Документ не разрешает Alibaba API calls, paid pilot, Kaggle scoring/training,
ослабление C gate или использование validation как источника генерации.
